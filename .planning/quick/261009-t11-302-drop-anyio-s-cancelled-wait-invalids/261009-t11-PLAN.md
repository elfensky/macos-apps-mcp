<objective>
Fix issue #302: UDS clients (the shim, the build's stream smoke, the install-agent prompt pass) intermittently log `Exception in callback Future.set_result()` / `asyncio.exceptions.InvalidStateError: invalid state` at teardown. The call result is never affected.

Cause (established by the orchestrator, do not re-derive): anyio's `_RawSocketMixin._wait_until_readable` / `_wait_until_writable` register the bare `f.set_result` as the selector callback and remove it only in `f`'s done-callback, one loop turn later. When the waiting task is cancelled in the same turn in which the socket becomes ready, the queued handle calls `set_result` on a cancelled future. asyncio's default exception handler logs that. Upstream anyio fixed only the `aclose()` variant.

Fix (locked by the orchestrator): one module-level asyncio exception handler in `daemon.py` drops exactly that case and passes everything else to `loop.default_exception_handler`. `_uds_client_factory` installs it on the client's running loop, and never replaces a handler someone else set. The stream smoke becomes a gate for any other loop exception.

Purpose: the build log is the release gate (`stream smoke ok`). A traceback above that line makes a good build look failed, or teaches a reader to ignore tracebacks there.

Output: three commits on `fix/302-uds-teardown-noise`; nothing pushed. The 20-run smoke count goes in the SUMMARY.

</objective>

Facts verified by the planner at `a596393` (do not re-derive):
- The race reproduces deterministically with public asyncio API on a fresh loop: create a future with `loop.create_future()`, cancel it, queue `loop.call_soon(f.set_result, None)` and `loop.call_soon(loop.stop)`, then `loop.run_forever()`. The handler receives a context with exactly the keys `message`, `exception`, `handle`. `context["exception"]` is an `asyncio.InvalidStateError`. `context["handle"]._callback` is the bound method: its `__name__` is `"set_result"`, its `__self__` is an instance of `asyncio.Future` and `cancelled()` is True. The selector reader handle anyio creates is the same `asyncio.Handle` type.
- `BaseEventLoop.call_exception_handler` calls `self.default_exception_handler(context)` through the INSTANCE when no handler is set. A custom handler is called as `handler(loop, context)`. So an instance attribute `loop.default_exception_handler = <recorder>` captures (a) every context when no handler is set and (b) every context that `_drop_cancelled_wait` passes on, while `get_exception_handler()` stays None. Tests and the smoke both use this; the smoke must NOT call `set_exception_handler` itself (that would stop the factory from installing the #302 handler).
