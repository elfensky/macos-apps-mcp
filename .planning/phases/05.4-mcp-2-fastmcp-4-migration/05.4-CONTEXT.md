# Phase 05.4: MCP 2 and FastMCP 4 migration

**Decision date:** 2026-11-03
**Status:** Ready for implementation; cross-model decision review complete
**Issue:** #470

## Scope and order

The MCP migration runs before the remaining bug fixes. The owner changed the order on 2026-11-03.
The new SDK may replace existing workarounds and change the best bug fixes.
After migration verification, reassess Phase 05.6 and the remaining milestones against the new architecture.
Phase 05.2 device acceptance remains incomplete. The migration does not close #348 or #516.

The baseline is commit `926ec99`. PRs #545, #547 and #546 merged on 2026-11-02.
The recorded claim that these PRs remain drafts is obsolete.

## Required behavior

- Upgrade MCP and FastMCP together to supported stable releases.
- Keep the Python 3.12 package floor and the Intel cryptography policy.
- Keep unlimited read duration between the shim and daemon. The connect deadline remains ten seconds.
- A stream that ends without an answer returns an explicit error. A destructive operation must never be retried automatically.
- Preserve the warning that an interrupted operation may have completed. Direct the caller to the audit log before retrying.
- Preserve client name, version and a stable identifier for each shim process in audit records.
- Treat caller labels as advisory metadata. They never authorize an operation.
- Preserve registration gates, annotations, dry-run defaults, notices and audit semantics.
- Keep all native calls behind the serialized runtime boundary.
- Keep Linux import and tools-list support.
- Run the complete unit suite, lint and formatting checks. Exercise the real local transport with synthetic tools.
- Verify the streamed-call smoke against both bundle architectures when build tooling permits.

## Architecture decisions under review

The candidate stable pair is FastMCP 4.1.6 and MCP 2.3.0. Upstream versions require fresh verification.
The migration should prefer supported SDK interfaces over copies of private SDK methods.
MCP 2 supplies abandoned-stream error handling. Behavioral tests must establish whether that handling replaces the existing patch.
If needed, an application-owned boundary should add the operation-outcome warning without replaying the request.
The httpx2 transport must use its own client, transport, timeout and exception classes consistently.
MCP 2 discards extra `Implementation` fields. Shim identity therefore needs a supported metadata channel.
An explicit local HTTP header is a candidate. Cross-model review must examine forwarding, sanitization and fallback behavior.

**eli14:** The SDK is the cable between the client and the server.
The replacement cable must carry the same signals and clearly report a broken connection.
A broken cable does not prove that the server stopped its work. Repeating a command could repeat a completed change.
