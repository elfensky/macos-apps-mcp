# MCP migration decisions

**Decision date:** 2026-11-03
**Status:** Accepted for implementation
**Evidence:** [Research](05.4-RESEARCH.md) and independent Claude transport probes.

## Supported SDK and transport

Use FastMCP 4.1.6 and MCP 2.3.0, with upper bounds below the next major versions.
Use httpx2 consistently for the local transport's client, transport, timeout and exceptions.
The local read duration remains unlimited. The connect deadline remains ten seconds.
Keep the Python package floor at 3.12 and preserve the Intel cryptography policy.

## Interrupted operations

Remove the private MCP 1 stream patch after equivalent regression tests pass.
MCP 2 already reports abandoned streams. The application must add the operation-outcome warning at the proxy boundary.
The warning states that the operation may have completed and directs the caller to the audit log before retrying.
Never repeat the request automatically.

FastMCP converts the SDK connection error into `ToolError` while retaining its cause.
A shim middleware can recognize `ToolError.__cause__` as `MCPError` with `CONNECTION_CLOSED` and add the warning.
The code must retain the exception cause for diagnosis.
The frontend receives a tool error, not the previous JSON-RPC error code.
Documentation and tests must reflect that distinction; the original numeric code is not a frontend compatibility guarantee.
Definite failures before execution, including refused connections and oversized requests, must not acquire the uncertain-outcome warning.

This boundary depends on exception chaining. Real transport tests must cover the chain and fail when an upstream change breaks it.
Test clean EOF without a result and daemon termination after dispatch. Verify prompt failure, one response and no replay.

## Caller identity and protocol compatibility

Read client name and version from the public snake-case `client_info` model.
Carry the shim identifier in an explicit HTTP header on its transport.
Read the header through FastMCP's public HTTP-context accessor, sanitize it and bound its length.
The identifier must remain stable across one shim's calls and differ between shim instances.
Caller identity and shim identifiers remain advisory. Neither can authorize operations.

The backend connection must mirror the frontend protocol era.
Use the public request context and public client mode setting; do not import the private SDK helper.
Legacy ping must work. Determine modern ping behavior from the modern protocol rather than assuming legacy behavior applies.
Verify initialization and no-context fallbacks explicitly.

## Response and request sizes

Set `max_sse_event_size=None` through the public transport option.
This preserves large local responses without introducing an arbitrary application limit.
The peer is the application's own daemon, reached through the restricted local socket.

Accept and document the SDK's 4 MiB HTTP request-body limit if no public FastMCP setting changes it.
The limit includes the serialized request envelope, rather than only one text argument.
A request rejected by HTTP 413 must not execute the tool or receive the uncertain-outcome warning.
Do not patch private request handling to remove this limit.

## Verification

- Run the complete unit suite, lint and formatting checks.
- Add real-session caller tests; update obsolete test doubles so they cannot hide a broken caller path.
- Cover both protocol eras, independent shim IDs, notifications, a call longer than five seconds and a response over 1 MiB.
- Exercise interrupted streams and oversized requests with synthetic tools and recorded execution counts.
- Preserve tool gates, annotations, dry-run audit values, notices and structured response data.
- Run Linux tools-list verification where available.
- Run the streamed-call smoke using both bundle architecture interpreters where available.
- Record unavailable device or bundle checks explicitly. Do not mark them passed.

**eli14:** The SDK is the cable between the client and the server.
The replacement cable reports a broken connection without a custom repair.
The warning still matters: a broken connection does not prove that the server stopped its work.
Repeating a destructive command could repeat a completed change.
