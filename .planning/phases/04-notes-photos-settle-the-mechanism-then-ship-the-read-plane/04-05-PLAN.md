osxphotos export facts (RESEARCH Pattern 6 and Pitfalls 4-5, run on the 0.77.2 wheel):
`PhotoInfo.export(dest, filename=None, edited=False, …, overwrite=False, increment=True, …)`
returns only the list of written paths and drops its errors; with `increment=True` (the
default) it renames on a clash, so `increment=False` is mandatory; `edited=True` on a photo
without adjustments raises ValueError; with the file not on disk it writes nothing, returns
`[]` and does not launch Photos. The published API docs show a download option as a default
that the 0.77.2 source does not have: trust the wheel, keep the `<0.78` pin (04-01), and pin
the call's keyword arguments in a test. Decide `absent` before exporting, from the source:
`path` / `path_edited` unset, or set to a path that is not an existing regular file (a
library can name an original that only iCloud holds); never from an empty result.

The three download option names the kwargs test must reject: `use_photos_export`,
`use_photokit`, `download_missing`.
