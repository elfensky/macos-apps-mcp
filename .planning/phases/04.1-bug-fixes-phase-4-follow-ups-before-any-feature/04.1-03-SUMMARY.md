# Phase 04.1 Plan 03: a killed export's staging copy is swept, cleanup errors are logged Summary

**export_photo sweeps dead-pid staging dirs — PR #394 (https://github.com/elfensky/macos-apps-mcp/pull/394), closes #387**

The staging directory is now `.macos-apps-mcp-export-<pid>-<8>`. On entry, `files.staging()` removes dead-process staging directories in the same parent, behind six guards. The `finally` cleanup logs an `OSError` as a WARNING that names the leftover directory and the pid. The body's result or typed error stands. `photos.py` and `lifecycle.py` are unchanged; no package was installed or locked.

## Sweep guards and the test that pins each

| Guard | Test |
|-------|------|
| Exact name, `fullmatch` (prefix, pid digits, 8 mkdtemp chars) | `test_staging_keeps_names_outside_the_exact_pattern` (7 cases: pid `0`, `1`, 20-digit, `x1`; suffix `abc`, `abcd1234.bak`, `ABCD1234`) |
| ASCII digits only in the pid | `test_staging_ignores_a_pid_written_in_non_ascii_digits` (added in review) |
| Real directory, not a symlink; the link target is never touched | `test_staging_never_follows_a_symlink_named_like_a_staging_directory` |
| Owned by this uid | not unit-tested: a directory of another uid cannot be made without root; the `st_uid != os.getuid()` check is in the same condition as the two guards beside it |
| Mode exactly 0700 | `test_staging_keeps_a_directory_wider_than_0700` |
| Pid is not this process's | `test_staging_keeps_its_own_process_s_directory` |
| Pid not alive: a live process's directory is kept | `test_staging_keeps_a_live_process_s_directory` |
| `PermissionError` from `os.kill` counts as alive | `test_staging_keeps_a_directory_whose_pid_answers_eperm` |
| Pids 0, 1 and an overflowing pid count as alive | the `0`, `1` and 20-digit name cases above, and the acceptance print `True True True` |

Every guard test plants a dead-pid control directory that must be gone afterwards, so a pass cannot be vacuous.

## Code review

No sub-agent tool was available, so the `code-review` skill could not run. An inline self-review of `origin/develop...HEAD` (spec: this plan, #387, D-11) checked the sweep against every never-remove rule and found one defect: the name pattern used `\d+`, which matches non-ASCII digits that `int()` also accepts, so a lookalike name could be read as a real pid. It was fixed with a RED test and then `[0-9]+` (see Deviations). No other open finding. Reviewed and found sound:

- A swap of the entry for a symlink between `stat` and `rmtree` is safe: `shutil.rmtree` refuses a symlink, and the fd-based removal does not follow links inside.
- Only `OSError` is caught in the cleanup; nothing wider.
- Nothing touches a file at dest; the sweep and the cleanup remove staging directories only.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Non-ASCII digits in the staging-name pid**
- **Found during:** Task 3 (self-review)
- **Issue:** `\d+` in a `str` pattern matches other scripts' digits, and `int()` reads them, so `...export-<Arabic-Indic digits>-abcd1234` was read as a pid and a 0700 directory of that name could be swept. This breaks "exact name pattern" and the threat model's "digits-only pid".
- **Fix:** RED test `test_staging_ignores_a_pid_written_in_non_ascii_digits` (failed: the directory was removed), then the pid group became `[0-9]+`.
- **Files modified:** `macos_apps_mcp/files.py`, `tests/test_files.py`
- **Commits:** `1f4b252` (test), `4c39558` (fix), merged hashes on develop
- **Effect on plan counts:** the total is +19, not the plan's +18; `-k "keeps or never_follows"` still reports 12 passed (the new test name does not match).
