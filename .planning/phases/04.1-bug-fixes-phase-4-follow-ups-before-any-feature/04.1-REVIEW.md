## Summary

No blocker found. The scrutinized area is `files._sweep_dead_staging` (#387), because it deletes directories in the user's file root. Its guards hold:

- The name must `fullmatch` `.macos-apps-mcp-export-<ASCII digits>-<8 of [a-z0-9_]>`, which is exactly what `mkdtemp` emits.
- The entry must be a real directory (`stat(follow_symlinks=False)`), owned by the current uid, at mode exactly 0700. A user-made `dest_dir` gets 0755 from `mkdir`, so it never qualifies.
- The pid must not be this process, must be above 1, and `kill(pid, 0)` must answer `ESRCH`. `EPERM`, `OverflowError` and every other answer keep the directory.
- `shutil.rmtree` refuses a top-level symlink and uses fd-based traversal, so a swap between `stat` and `rmtree` cannot redirect the delete.
- The scan is one level deep, in `dest.parent` only.
- A live exporter's directory cannot be removed, because a live pid always answers. A pid reused by a stranger can only keep residue.

I found no path where anything other than a dead export's own staging directory is deleted.

Verified by running the code:
- The `uv build --build-constraints … --require-hashes` command builds the wheel from the `build` group export.
- It fails closed when a build requirement has no hash.
- The 232 tests in the four changed test files pass.
- `ruff check` is clean.

Remaining findings are about observability of the sweep, a partial-batch effect of the #383 retyping, and small robustness and bundle-content points.

## Warnings

### WR-01: The sweep deletes in the user's Downloads root but its only trace is an INFO log that nothing emits

**File:** `macos_apps_mcp/files.py:214`
**Issue:** The removal is logged with `logger.info(...)`. No module configures logging (`grep basicConfig|StreamHandler` finds nothing), and Python's last-resort handler prints WARNING and above only. So in daemon and stdio mode a deletion in the user's own directory leaves no record at all. It is also not in the audit JSONL, which is the project's trail for "every write". The failure path (`logger.warning`) is visible, the success path is not. When a user asks "what removed that folder", there is no answer.
**Fix:** Log the removal at WARNING, or at least on the `macos_apps_mcp` logger at a level the daemon emits. Optionally write one `audit_write` record per removed directory.
```python
logger.warning("removed staging directory %s left by dead pid %s", e.path, m[1])
```

### WR-02: `export_mail` refuses mid-batch after earlier files are already written, and the typed refusal hides that

**File:** `macos_apps_mcp/adapters/mail.py:2495` (interacts with `files.exists_refusal`, `files.py:160`)
**Issue:** `export_mail` calls `files.target_path` and then `path.write_bytes` once per message. If message 1 is written and message 2 meets an existing file, `WriteRefused` is raised out of the loop. The `results` list is discarded, so the model sees only `<path> already exists — this never overwrites. Choose another dest_dir…`. The message does not say that a file was already written. The model that follows the advice and retries with another `dest_dir` gets duplicates. A retry with the same `dest_dir` is refused on message 1 now. This behavior existed before (as a raw `FileExistsError`), but #383 made it a deliberate agent-facing contract, and the test only covers a single-id batch.
**Fix:** Check every target first, before the first write, and refuse the whole batch. Compute `target_path` for all located, non-absent ids up front, then write. If per-id reporting is wanted, catch `WriteRefused` per id and report `status: "exists"` like the `absent` case.

## Info

### IN-01: The sweep's "never raises" contract holds only for `OSError`

**File:** `macos_apps_mcp/files.py:203`
**Issue:** `_pid_alive(int(m[1]))` sits outside the `try`. `_pid_alive` handles `ProcessLookupError`, `PermissionError` and `OverflowError` only. Any other error from `os.kill`, or from `int()` (the 4300-digit limit cannot be reached with a 255-byte name today), would escape `staging()` before `mkdtemp` and fail the export. The `finally` path was carefully made non-raising. The entry path is not held to the same rule, although a failed cleanup of OTHER people's residue should never fail the user's export.
**Fix:** Wrap the per-entry body (including the `_pid_alive` call) in the existing `try/except OSError`, or `except Exception` with the same warning.

### IN-02: The bundle now carries a random temp path in `direct_url.json`

**File:** `scripts/build_app.sh:140`
**Issue:** Installing `"$WORK"/wheel/*.whl` makes uv write `macos_apps_mcp-*.dist-info/direct_url.json` with `file:///<mktemp dir>/wheel/…whl` (confirmed by a trial install). It differs on every build and records the build machine's temp path inside a signed bundle. The old directory install recorded the repo path, which was stable. Nothing breaks, but two builds of the same commit are no longer byte-identical.
**Fix:** Delete the file after the install (`rm -f "$SITE"/macos_apps_mcp-*.dist-info/direct_url.json`) before the signing seal, or accept and document it.

### IN-03: `resolve_dest` failure text claims "nothing was written" and always advises another path

**File:** `macos_apps_mcp/files.py:135-142`
**Issue:** `mkdir(parents=True)` can create intermediate directories before the failing component, so "nothing was written" is not strictly true (for `a/b/c` where `a` is created and `b` is refused). The advice "Choose another dest_dir… or fix the permissions" is also wrong for `ENOSPC` or `EROFS`, where the path is not the problem. If `e.strerror` is `None` the text shows "(None)".
**Fix:** Say "no file was written" (not "nothing"), use `e.strerror or e.__class__.__name__`, and drop the "choose another dest_dir" clause for ENOSPC/EROFS, or word it as "if the volume is full or read-only, free space or remount it".

### IN-05: `import` can return `missing value`, and the script then fails with an opaque error

**File:** `tests/integration/test_photos_integration.py:55`
**Issue:** `return id of item 1 of imported` assumes the import produced at least one item. photoscript guards this case (`if theItems = missing value then return {}`). When Photos imports nothing (an unsupported file, or a refused import), this line raises an AppleScript error about `item 1` of `missing value`, not a clear "nothing imported". This line is not part of cd931dc and the failure is loud. It only costs diagnosis time on a device run.
**Fix:** Add `if imported is missing value then error "Photos imported nothing"` before the `return`.
