# Plan 04: Adapters reads the last Health report

## Required end state

The Adapters page uses the last completed Health report for permission chips.
Automation uses Health's existing live/TCC merge. Other grants use that report's TCC identities and read reasons.
Live granted, denied, and not-asked answers override stale Automation rows for the same app.
An unknown live result retains the existing TCC fallback.
Combined permission precedence remains denied, not asked, unknown, then granted.
An Automation grant cannot hide a Full Disk Access denial.

Before the first completed report, chips retain their existing TCC-only behavior.
One muted line links to Health. After completion, that line identifies the report and its local completion time.
Failed and unfinished checks preserve the last completed report and its time.
Adapters rendering makes no native call and adds no wait guard.

**eli14:** The permission chips display a dated inspection card.
A failed or unfinished inspection leaves the previous card visible.
Today's page stays responsive. Later permission changes require another Health check.

## Implementation

1. Add `checked_at` to the report published by `health._run`, after diagnosis and TCC reasons finish.
   Publish all three values together. Preserve the lock, timeout, abandonment, and Health rendering contracts.
2. Read `health._last` through the public `health.last_permissions` accessor and a local import during Adapters rendering.
   Capture one report reference for both chips and the source note.
   Query TCC only when there is no completed report.
3. Reuse `_automation_state` per Automation service and `_state` for other services.
   Extract the existing aggregate precedence into one small pure function in `grants.py` for both rendering paths.
4. Render the local timestamp with seconds through `h`, using existing muted-note styling and a Health link.
