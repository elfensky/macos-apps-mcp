# Phase 05.6: Bug fixes — Notes write safety and system folders in any language (#500, #501, #497, #471, #521, #540) - Context

**Gathered:** 2026-11-01 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Every Notes write keeps the note's content or refuses before it touches the note, and system
folders are found in any language. Six bugs, one phase, before the next feature phase (bugs
before features, owner 2026-10-11):

- **#500:** `update_note` and `delete_note` refuse locked and shared notes. A note with
  attachments or non-text content is refused unless the device probe proves the content
  survives. The full HTML body is the before-state of every update.
- **#501:** Notes' Recently Deleted is excluded by `ZFOLDERTYPE` on the SQLite path and by a
  translated name table on the AppleScript fallback. Mail's Trash, Junk, Sent and Archive are
  found by translated names in the one vocabulary in `mailbox_url.py`.
- **#497:** the Adapters page shows the live Automation grants on macOS 27, from the last Health
  report, with no native call.
- **#471:** the signed `.app` carries the licence text of every bundled package whose wheel ships
  none, and the build fails when one is missing.
- **#521:** `delete_draft` finds the draft's mailbox in the Envelope Index and deletes with one
  `whose message id is` query on that mailbox. It keeps the dry run and the exactly-one-match
  check, so a busy Mail no longer times out at 30 s.
- **#540** (filed and folded in at this session, owner 2026-11-01): the state folder and its
  private files can be read only by the account that owns them.

Out of this phase: Notes Markdown input and attachment tools (Phase 05.8, which builds on the
guards made here); a Notes undo tool; Notes backups on the dashboard or in `purge_backup`; i18n of
`mail_reply_cleanup.py`; the 25-record cap of the `drafts` listing itself; any change to
`mail_outgoing.py` or `mail_reply_cleanup.py` (Phase 05.2 still runs on them).
</domain>

## Implementation Decisions

### Notes write guards (#500)
- **D-01:** **One AppleScript guard handler, composed into every Notes write script.** A handler
  (for example `on noteRefusal(n)`) is prepended to `_DELETE`, `_PREVIEW_DELETE`,
  `_UPDATE_NOTE` and a new update-preview script, the way `mail_addressing.MAILBOX_REF` is
  prepended to Mail scripts. It returns a status word before any change: the `_SWEEP_DELETE`
  pattern (`mail_outgoing.py:706-724`). One Python mapper in `notes.py` turns the word into
  `WriteRefused` and names the cause (locked, shared, or what would be lost). No change to
  `runtime._classify_osascript_failure`: today a script's own `error "…"` becomes a generic
  `NativeError` (`runtime.py:182-209`), and no code maps it to `WriteRefused`. Phase 05.8 reuses
  the handler and the mapper.
- **D-02:** **Locked = `password protected of n`. Shared = `shared of n` OR
  `shared of container of n`**, because a note in a shared folder is visible to other people.
  Both are in `Notes.sdef` (`:128`, `:131`, folder `:92`). The folder check stays even if the probe
  shows that note-level `shared` already covers folder shares (fail safe).
- **D-03:** **Non-text content: refuse the full replace by default and name what would be lost.**
  The device probe (D-23) can only relax this default to "allow, with the backup". It can never
  widen what a write may lose. The probe also picks the signal: `count of attachments of n`
  (AppleScript), plus a checklist signal (an HTML marker in `body of n` read in the same script if
  the probe finds one; else `ZHASCHECKLIST` from NoteStore, refusing when the store cannot be
  read). Delete checks only locked and shared: a deleted note keeps its attachments in Recently
  Deleted.
- **D-04:** **The guard fails closed.** A property read that errors stops the script before
  `set body` or `delete`.
- **D-05:** **The update dry run runs the same guard script.** That script also returns the
  current title and body size from Notes. So the preview refuses exactly as the real call does
  (#54), and review item WR-01 (`body_chars: 0` when hydrate fails, `01-REVIEW.md:115-140`) closes.
  The SQLite `get_bodies` read leaves `_update_preview` (`notes.py:862-889`).

### Before-state backup (#500)
- **D-06:** **The backup is written before `set body`, in the same script.** `_UPDATE_NOTE` reads
  `body of n` (HTML) and writes it to a file that Python created empty at `0600`:
  `state_dir()/backup/notes/<stamp>-p<pk>.html`, in a `0700` folder. The path convention is
  `mail_recover._backup_dir` (`mail_recover.py:316-322`). The private-file pattern is
  `deploy._atomic_write` (`deploy.py:390-403`). The AppleScript `write … as «class utf8»` sits
  outside the `tell application "Notes"` block. A failed backup write stops the script before
  `set body`. If the in-script write proves fragile, the planner may use two calls instead: the
  preview script returns the HTML, Python writes it at `0600`, and the update script refuses with
  `changed` when `body of n` differs from the saved copy. Both give the same guarantee.
- **D-07:** **The `update` result gets a `backup` key (the file path).** The audit `after` field
  then points to the file with no change to `audit.py` (`audit.py:235-241`). `notes.snapshot`
  stays title-only.
- **D-08:** **Notes backups are kept like Mail backups: until deleted by hand, `0600` files in
  `0700` folders** (owner, 2026-11-01). Phase 4 D-13 (no on-disk copy of note text) covers the
  whole-library search index, not a per-write before-state. Locked notes are refused, so they are
  never copied. Accepted trade-off: a credential in an overwritten note stays on disk.
- **D-09:** **Notes backups stay out of `backup_usage`, `backup_advisory`, `purge_backup` and
  the dashboard Backups pages in this phase.** All of those are wired to `backup/mail`. A restore
  is done by hand from the HTML file.

### System folders (#501)
- **D-10:** **Notes SQLite path: exclude `ZFOLDERTYPE = 1`, not the name.** Use the NULL-safe
  form `(f.ZFOLDERTYPE IS NULL OR f.ZFOLDERTYPE <> 1)`. `ZFOLDERTYPE` joins `_FINGERPRINT`
  (`notes.py:61-76`), so a store without the column degrades to AppleScript. Checked 2026-11-01
  (read-only): type 1 is the only trash folder, and the name rule and the type rule exclude the
  same notes, on all 39 live notes.
- **D-11:** **Notes AppleScript fallback: a translated "Recently Deleted" name table in
  `notes.py`.** Start from nucleus-apple-mcp's 27-language list. Pass the table as argv to
  `_LIST_ALL` (`if name of f is not in trashNames`, `notes.py:115`). The integration cross-check's
  `_RECENTLY_DELETED_IDS` (`tests/test_integration.py:1117-1134`) uses the same table. The Notes
  folder class has no type property (`Notes.sdef:74-100`).
- **D-12:** **Mail: translated names in the one vocabulary in `mailbox_url.py`** (`_SPECIALS`,
  `SENT_LEAVES`), so every user gets them at once: the trash query, `mail_undo`, the copy rank,
  dedupe and the awaiting-reply scan (owner, 2026-11-01). The `.mboxCache.plist` role bits are
  not used: the file is a private Apple cache, and it does not cover Exchange or On My Mac.
  Languages: at least nl, de, fr and ru (the issue's acceptance), plus the names the researcher
  finds for Gmail (`[Gmail]/…` and `[Google Mail]/…`), Exchange and iCloud.
- **D-13:** **Fix today's English and encoding gaps in the same change.**
  - Add Exchange `Deleted Items` (trash) and the Exchange Junk spelling. Today `trash_mail` finds
    no Trash for the EWS account.
  - The LIKE patterns match a non-ASCII leaf. Today `_like_leaf` (`mailbox_url.py:51-54`) encodes
    only spaces, so no non-ASCII leaf can match. Mail stores percent-encoded UTF-8 with uppercase
    hex and leaves `&()` unencoded. Emit both the NFC and the NFD form of each name.
  - `is_trash` compares an NFC-normalized, casefolded leaf.
  - Normalize only inside the classification compares. Never normalize a `path()` or `leaf()`
    value that addresses a mailbox in Mail: facts §5 says a leaf read back does not round-trip.
  - Unit fixtures use the stored shape found on this Mac: percent-encoded UTF-8, some NFD, no
    modified UTF-7. Here 33 of 155 leaves are Cyrillic, and 3 of them are NFD.
- **D-14:** **`mail_reply_cleanup.py` does not change.** Its `_is_sent_url` reads
  `mailbox_url.path()` and `SENT_LEAVES`, so it gets the new names through the import. A case or
  NFD variant there stays `unproven`, and `unproven` deletes nothing (facts §4e). i18n of that
  file waits until Phase 05.2 closes.

### delete_draft (#521)
- **D-18:** **Find the draft in the index, then delete with `_SWEEP_DELETE`, unchanged.** The
  lookup is `mail_index.query_message_locations([stored_id(mid)])` (`mail_index.py:1304-1321`)
  plus `mail_addressing.mailbox_args(url)` (`:91`). The delete imports
  `mail_outgoing._SWEEP_DELETE` and does not edit it. `mail_drafts` already imports
  `mail_outgoing`, so there is no import cycle. The sweep's answers map as follows:
  - `deleted`: success.
  - `alive`: "may be left", never a success claim.
  - `several`: a refusal, with nothing deleted.
  - `gone`: no such draft.
  The sweep's one `delay 3` verify is accepted.
- **D-19:** **The fast path runs only when the index gives exactly one live row, or exactly one
  row in a Drafts mailbox.** A Drafts mailbox is `Drafts`/`Draft` at the account root or under
  Google's root. Everything else uses today's unified walk, which is slow and never wrong:
  several candidate rows, or no row at all (a fresh draft, index lag, no Full Disk Access, or the
  Sequoia floor, `SchemaDrift`).
- **D-20:** **The dry run and the audit snapshot find the draft the same way as the real call.**
  They use the index lookup plus the same `whose` count, with no delete. They do not use the
  25-record `_DRAFTS` walk (`mail_drafts.py:93-127`), so the preview stops saying "no draft" for
  drafts past the first 25 (287 drafts at the 05.2-09 sitting). `_drop_sent_draft`
  (`mail.py:1294-1307`, used by `send_mail(draft_id=…)`) gets the fix through the shared function.
- **D-21:** **Two edits to the Mail facts doc, rebased last** (05.2-13 may edit the same doc).
  The device result (D-23) narrows §6 ("`whose` is unreliable on the Drafts mailbox", `:629`).
  The `:397` claim that the `account` class declares the special mailboxes is corrected: in the
  macOS 27 `Mail.sdef` they are on the application only (`:320-406`), not on `account`
  (`:626-700`).
