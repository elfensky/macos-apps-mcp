# 05.6-01 — Private state storage

The implementation creates the state directory at `0700` and narrows existing group or other permissions before use.
CLI startup attempts the same protection before serving or starting a storage-writing CLI role.
Failure produces a bounded stderr warning. Tool listing and diagnostics remain available.
Each private storage writer rechecks protection. Native actions retain the existing best-effort audit policy.
Existing owner-only modes remain unchanged. Existing file modes and unrelated paths remain unchanged.

**eli14:** The state directory is a locked cabinet. Its lock protects every existing paper inside.
New backup folders and files also receive their own locks. The installed cabinet still needs its device check.

## Delivered behavior

- `state_path()` resolves the configured location without creating or repairing it.
- `private_directory()` rejects directory symlinks and foreign ownership before chmod.
  A directory descriptor binds the ownership check and chmod to the same object.
- `state_dir()` retains the previous exposed mode after a successful repair, in process memory only.
- Doctor reports current exposure, private permissions, an earlier repair, an absent directory, an unsafe path, or an inspection failure.
  Its state check precedes probes that can repair storage. Backup usage inspection no longer creates or repairs state.
- Mail backups use `0700` directories at each owned component and exclusive `0600` file creation.
  Existing backup destinations are refused. Symlinks cannot redirect backup directory writes or file creation.
- Backup destination failures abort before the Mail action. A failed file write removes its incomplete output.
  An unreadable source still produces the established absent-backup result.
- A completed Mail action returns the already-checked backup path. Result assembly performs no further permission repair.
- Dashboard backup path resolution is read-only.
- Audit storage reports failure when state protection fails. Audit readers retain their documented error results.

## Remaining acceptance and limits

The installed-daemon `stat` check remains pending. Acceptance requires `0700` (`drwx------`) at its actual state directory.
The installed daemon's build, version, and doctor result must accompany that evidence after a separately authorized installation.
No installation, restart, signing, release, device integration run, Mail send, or personal-data mutation occurred in this task.

The local tests establish POSIX mode behavior. They do not establish installed-device acceptance or live Mail behavior.
The mode check does not evaluate macOS ACL entries. An ACL can grant access despite mode `0700`.
Old files retain their existing modes under the private parent, as D-22 specifies.
The repair record lasts for the current process; it is not a persistent history of earlier exposure.
Audit persistence remains best-effort, as before this change. A native action can complete without an audit record if logging fails.
This fix protects private storage; it does not introduce a mandatory audit gate for every native action.
Independent review identified corrected startup and post-action result defects. Updated CI remains pending. Issue #540 remains open until verification.
