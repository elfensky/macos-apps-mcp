## Summary

The phase holds nine requirements. Seven are public bug fixes (FIX-27, FIX-30 to FIX-35). Two are private security advisories (FIX-28, FIX-29), which are developed outside the public planning files. No fix needs a new dependency. Each fix has a helper in the code base or in the standard library that does the work.

Two results came from prototypes in `05.12-proto/` and change what the issues propose:

1. **FIX-34.** A linear form exists that gives exactly the output of the two old patterns. A differential run found 0 differences in 8,000 generated Mail-layout reply bodies and 0 in 200,000 crafted texts. The form that the review proposed (`\b` after the tag name, `<[^<>]+>` for tags) differs in 1,536 of the same 8,000 bodies. The exact form must be used.
2. **FIX-27.** A plain HTTP GET on the daemon's unix socket reads the version and the build in 6 ms while a tool runs. A daemon without the route answers 404. A socket file that nothing listens on still exists, so the present wait (`socket_path().exists()`) returns too early after a restart.

Two more results size the work:

3. **FIX-35.** PR #584 closed five of the six gaps. The open part is the lock for the store paths and the `files` root. It is a real gap: an audit run of the default suite found 23 tests in 8 files that open a real store of the Mac (20 open Mail's Envelope Index, 3 open the Notes group container).
4. **FIX-30.** 40 scripts address Mail by name. One more script (`doctor._PROBE`) addresses each of six apps by a name given at run time. Apple's documentation says the id form works as a `tell` target, needs no running app, and is the form for distributed scripts. A scan of the app bundles on macOS 27.2.1 shows that Notes, Messages and Music also hold nested bundles that carry the app's name, in `CFBundleDisplayName`.

**eli14 summary.** Think of the daemon as a shopkeeper who stays in the shop after the shop was rebuilt around him. FIX-27 makes the front door ask "which shopkeeper is in?" through a private hatch and swap him when he is the old one. FIX-30 stops calling Mail by its first name, because a small helper inside Mail has the same first name and answers when Mail is out; the fix uses Mail's passport number. FIX-31 to FIX-33 are about a courier who puts a note on top of a letter: he must say which check failed, must not take the owner's own footer for the old letter, and must leave no loaded stamp behind when he gives up. FIX-34 makes the reader of old letters read each page once, also when a stranger sends a page built to waste time. FIX-35 puts a lock on the real filing cabinets, so a test cannot open them by accident. Today these bugs cost a confusing error or a safe refusal. Later, with more users, the same gaps cost a stuck upgrade, a reply sent without its quote, or text in the wrong draft.

**Primary recommendation:** Plan six public lanes (FIX-34, FIX-27, FIX-30, FIX-35 in parallel; then one lane for FIX-31, FIX-32 and FIX-33 after one measurement sitting), one private lane for FIX-28 and FIX-29 after the public lanes merge, and one acceptance sitting on the signed build.

### FIX-27 (#568): the app after an upgrade

**What exists.**

- `launch` compares nothing. It checks the agent status and opens the dashboard. [VERIFIED: macos_apps_mcp/deploy.py:322-366]
- The daemon captures its identity at import. Verbatim: `_SERVING_VERSIONS = {d: _read_version(d) for d in ("macos-apps-mcp", "mcp", "fastmcp")}` and `_SERVING_BUILD = _read_build_stamp()  # #574: read once at import, like the versions`. `doctor.version()` and `doctor.build_stamp()` return them. The stamp is `<short-sha> <utc-build-time>`; a checkout without a stamp file reports `"dev"`. [VERIFIED: macos_apps_mcp/doctor.py:390-425]
- The restart call exists once. Verbatim: `["launchctl", "kickstart", "-k", f"gui/{os.getuid()}/{BUNDLE_ID}"]`, inside `allow_send`. [VERIFIED: macos_apps_mcp/deploy.py:594-598]
- The wait proves a file, not an answer. Verbatim: `def _wait_for_socket(timeout: float = 30) -> None:` with `if socket_path().exists():`. [VERIFIED: macos_apps_mcp/deploy.py:217-225]
- The uncertain-outcome answer exists. Verbatim: `"daemon connection ended without a result — "` `"the operation MAY HAVE COMPLETED; check the audit log "` `"before retrying anything destructive"`. A connect failure does not get it. [VERIFIED: macos_apps_mcp/daemon.py:221-248]
- A test already kills the server during a call and checks that answer, in every protocol mode. Verbatim: `@pytest.mark.parametrize("kind", ["eof", "kill", "silent-kill"])`, `assert WARNING in result.content[0].text`, `assert executions(root, "disconnect") == 1`. [VERIFIED: tests/test_mcp_transport.py:207-233]
- `launchctl kickstart -k`: "If the service is already running, kill the running instance before restarting the service." [CITED: `man launchctl` on macOS 27.2.1]
- The agent plist sets `KeepAlive` and `ThrottleInterval` 10 s. [CITED: docs/DAEMON.md:528-530]
- "When a job dies, launchd kills any remaining processes with the same process group ID as the job." [CITED: `man launchd.plist`, key `AbandonProcessGroup`]

**How `launch` reads the identity without a tool call that needs a grant.** A route on the FastMCP app, `GET /identity`, returns `{"version": …, "build": …}` from `doctor.version()` and `doctor.build_stamp()`. `FastMCP.custom_route(path, methods, name=None, include_in_schema=True)` exists in fastmcp 4.1.6. [VERIFIED: `inspect.signature` in the project venv]

The prototype served the route through `daemon.make_dispatcher` on a temp socket and read it with `httpx2`. Output of `05.12-proto/identity_route_probe.py`: [VERIFIED: prototype run, 2026-11-20]

```
1. route on the UDS: 200 {'version': '9.9.9', 'build': 'abc1234 2026-11-20T00:00:00Z'}
2. a daemon without the route: 404
3. route during a running tool: 200 in 6 ms
   the tool then answered: ['done']
4. stale socket file (exists: True ): ConnectError [Errno 61] Connection refused
   absent socket file: ConnectError [Errno 2] No such file or directory
```

Consequences for the design:

- The route needs no MCP session, no tool, no native worker and no grant. It answers while a tool holds a worker thread.
- The dispatcher sends only unix-socket requests to the MCP app. So the route is not reachable on the dashboard's TCP port. [VERIFIED: macos_apps_mcp/daemon.py:142-160]
- Every released daemon (up to 0.16.1) has no route and answers 404. "Not 200" therefore means "an older daemon": restart.
- "No answer" (connection refused, no file) means the daemon is down or is starting. `launch` must wait and must not kickstart: a kickstart would kill a daemon that is in its slow first start. A socket that accepts and stays silent (a read timeout, a read error) is "no answer" too: `daemon.bind_socket()` listens before uvicorn serves, so a daemon in its start accepts the connect, and a daemon of the same version whose loop is busy can time out. Only an HTTP answer is a reason to restart: a 200 with another identity, or a status without the route (404). A wedged old daemon then ends at the alert of the bound, which names the kickstart command. [CORRECTED at the plan revision, 2026-11-20]
- The wait must prove an answer. After a kill the socket file stays (line 4), so `socket_path().exists()` is true at once and the dashboard would open on a dead port.

**What the first start of a new bundle costs.** Two observations exist: about 2 min 20 s from the start to the first answer, twice; calls before that got `Connection refused`. [CITED: .planning/phases/05.2-…/05.2-20-SUMMARY.md:105-106, and the device note of 2026-11-19 in the phase brief]. The cause was not measured. The present 30 s bound is shorter than that start. The bound should be 300 s (at least twice the largest observed start), stated as calculated, and checked at the acceptance sitting. [ASSUMED: 300 s]

**What `launch` should show.** An opened app has no window and no Terminal. During a wait of minutes the person sees nothing. The smallest form reuses the `_alert` script shape (`display alert`) in a child process that does not block: start it when the wait begins, end it when the daemon answers. The text names the version change, says that the first start after an update can take a few minutes, and says that MCP clients must reconnect. The look is an owner decision (see the table).

**What a connected client sees.**

| Moment | Answer | Source |
|---|---|---|
| A call is in flight at the kill | The shim's warning ("MAY HAVE COMPLETED"); the call is not replayed | [VERIFIED: tests/test_mcp_transport.py:207-233] |
| A call arrives before the new daemon answers | A tool error from the connect failure, without the warning (a definite refusal) | [VERIFIED: tests/test_mcp_transport.py:227-230, verbatim `assert refused.is_error and WARNING not in refused.content[0].text`] |
| After the new daemon answers | The client's shim is the old shim process until the client reconnects | [CITED: docs/DAEMON.md:254-258] |

The requirement asks for no new mechanism here. The plan confirms the existing test and adds no replay.

[VERIFIED: macos_apps_mcp/doctor.py:182-189]

**What the id form changes.** From Apple's documentation:

- "It is now possible to simply address an `application` object by id, where the id is either the bundle identifier or the four-character signature code. For example, `application "Mail"`, `application id "com.apple.mail"`, and `application id "emal"` all refer to Mail.app, and will all work as the target of a `tell` block". "This does not require that the application be running." [CITED: developer.apple.com/library/archive/releasenotes/AppleScript/RN-AppleScript/RN-10_5/RN-10_5.html]
- "Scripts intended for distribution should use the id form. That way, the script will continue to work even if the user has changed the name of the application." [CITED: same]
- "When running a script, if an application specified by id is not found, AppleScript will not ask where it is. It will throw an error, which can be caught using a `try` block." [CITED: same]
- "Statements within a `tell` statement that use terminology from the targeted object are compiled against that object's dictionary." [CITED: developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/reference/ASLR_control_statements.html]
- "AppleScript has always launched applications if it needed to in order to send them a command. … AppleScript now launches applications hidden by default." [CITED: RN-10_5]
- `running`, `name`, `id`, `version` and `frontmost` are answered "without launching the application or sending it an event". [CITED: developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/reference/ASLR_classes.html]

So the compiler still needs Mail's dictionary when Mail is addressed by id. What changes is the lookup key: a bundle identifier, which only Mail.app has, in place of a name that three bundles share.

**Is `using terms from application id …` needed?** No. "Whereas a `tell` statement specifies the default target … *and* the terminology to use, a `using terms from` statement specifies only the terminology." It is meant for handler scripts such as Mail rules and for a target "that may not be available when you compile the script". [CITED: ASLR_control_statements.html] Every script here uses Mail terms inside a `tell` with a literal target, and raw codes (`«class mssg»`) where it does not. A literal `tell application id "com.apple.mail"` gives both the target and the terminology.

The same script by name fails with -2741. [CITED: issue #585]

The name is available from the same pattern.

### FIX-31 (#607): the window check

**What exists.** `_hold_window`: when the check fails, one `_ACTIVATE_WINDOW` script (`activate`, then `set index of window id wid to 1`), `time.sleep(_ACTIVATE_WAIT_S)`, one more check, one refusal text for both halves. [VERIFIED: macos_apps_mcp/runtime.py:870-891]

**The platform rule.** Since macOS 14 activation is a request:

- "Use this method to request app activation; calling this method doesn't guarantee app activation." [CITED: developer.apple.com/documentation/appkit/nsapplication/activate()]
- "Cooperative activation addresses this problem by making app activation a request instead of a command." "The system dynamically determines whether to grant activation state based on the context." "People ultimately decide which apps gain focus by activating them through their device's user interface." [CITED: developer.apple.com/documentation/appkit/passing-control-from-one-app-to-another-with-cooperative-activation]
- "Only the active app can influence the activation context. It does so by yielding to an explicit target app before the target app activates. … If the system honors the request, the active app deactivates, and the target app activates. Otherwise, the active app remains active." [CITED: same]
- `yieldActivation(to:)`: "Calling this method doesn't deactivate the yielding app, nor does it activate the app you yield to." [CITED: developer.apple.com/documentation/appkit/nsapplication/yieldactivation(to:)]

What follows for this tool:

- The daemon is a background agent. It is never the active app, so it cannot yield. It can only ask Mail to activate (`tell … to activate`), and Mail then requests activation for itself. How the system weighs recent input in another app is not documented. [ASSUMED]
- A request that the system declines does not arrive later. A longer wait fixes a late activation only. A declined activation needs the refusal with a directive.
- Forcing the focus again is not safe. While the person types in another app, an activated reply window would receive the keys.
- The device facts fit both readings: Mail was active 116 ms after `activate` in a quiet state (21 of 21 reads over 4 s), and was not active right after the refused call that followed a click in another app.

**Design (prescriptive).**

1. One activation script, as today. No second activation.
2. A bounded poll of the cheap half only: read `AXFrontmost` every 50 ms until it is true or `_ACTIVATE_WAIT_S` ends. No Apple Event runs inside the loop (facts §8: never leave a polling loop pointed at Mail).
3. When Mail is active, read the window index once.
4. Two refusal texts, both starting with `window check:` (three tests match that prefix). Each names the half and gives the directive, in the form of `_CLIPBOARD_CHANGED`.
5. The bound comes from the device step. Until then the value is 2.0 s, stated as calculated. [ASSUMED: 2.0 s]

The poll changes the time of the refusal path only. A held window returns at the first check, as today.

### FIX-34 (#611): the HTML strip in linear time

**The two patterns.** Verbatim: `chunk = re.sub(r"(?is)<(script|style).*?</\1>", "", chunk)` and `parts.append(html.unescape(re.sub(r"<[^>]+>", " ", chunk)))`. [VERIFIED: macos_apps_mcp/adapters/mail_reply_cleanup.py:305-307] Each repeats a scan that cannot succeed: the first from every opener with no closing tag, the second from every `<` after the last `>`.

**The exact linear form (prescriptive).** Both helpers return what the old `re.sub` returns, for every input. They remove only the repeated scans.

- Tags: no tag can end after the last `>`. Cut the text there, run the old pattern on the first part, append the rest. Before the last `>` each `<` meets a `>`, so each attempt ends there.
- Blocks: the old pattern can match only where an opener starts. Find openers with `(?i)<(script|style)`. Try the old pattern at the opener with `match`. A failed try means that no closing tag for that captured name exists from there on, so a later opener with the same name also fails: remember the name and skip it. Only a small fixed set of names can fail: `script`, `style`, and the spellings with a letter that case-folds to `s` or `i` (8 names in the measured worst case). So the number of scans that reach the end of the text does not grow with the size of the text.

The code is in "Code Examples". It keeps the old pattern object, so the case rules of the pattern (the backreference included) are the same by construction.

### Anti-Patterns to Avoid

- **A timeout on the shim↔daemon hop to "wait out" the restart.** That is #170. The identity read is a separate request with its own short timeout.
- **`socket_path().exists()` as proof of a running daemon.** The file outlives a killed daemon.
- **A kickstart when nothing answers.** It kills a daemon in its slow first start and starts the wait again. A read timeout on a socket that accepts counts as "nothing answers".
- **A `doctor` tool call from `launch`.** It queues behind the native worker.
- **An `osascript` call inside a polling loop** (facts §8). Poll the Accessibility read; read the index once.
- **A second activation of Mail.** It takes the focus from a person who is typing.
- **The review form of the HTML strip.** It is not output-equal.
- **A cap on the file size of every new row.** An unthreaded row needs its headers only; a large incoming mail would make every sweep `unproven`. Cap the body of a threaded candidate.
- **Advisory content in a branch name, a commit message or a plan title.**

## Common Pitfalls

### Pitfall 1: the wait returns on a stale socket file
**What goes wrong:** the dashboard opens on a port where nothing listens, or the first open reports a daemon that is not there.
**Why it happens:** `kickstart -k` kills the daemon; `serve()`'s `finally` does not run; the file stays.
**How to avoid:** wait until `GET /identity` answers, and for an upgrade until it answers with the bundle's own version and build.
**Warning signs:** a unit test that passes with a file made by `touch`.

### Pitfall 2: the bound is shorter than the first start
**What goes wrong:** an alert says the daemon never appeared, while it is starting.
**Why it happens:** 30 s against an observed 2 min 20 s.
**How to avoid:** a bound of at least twice the largest observed start, and a visible wait. Never kickstart on a transport error: the starting daemon listens on its socket before it serves, so a connect that succeeds with no answer is a start in progress, not an old daemon.
**Warning signs:** "daemon socket never appeared" after an install; a `TransportError` branch that returns anything but `None`.

### Pitfall 3: the timeout hint disappears with the id form
**What goes wrong:** a wedged Mail gives the generic timeout text without the force-quit directive.
**Why it happens:** `_TELL_APP` matches the name form only.
**How to avoid:** change the pattern and the hint tests in the same commit as the scripts.
**Warning signs:** `_timeout_hint(<an id-form script>) == ""`.

### Pitfall 4: `_alnum` is case-sensitive
**What goes wrong:** a test with a hand-typed lower-case tail never matches.
**Why it happens:** `_alnum` keeps case; the real tail comes from the original's own text.
**How to avoid:** build test tails from the test body's own words.
**Warning signs:** a count-rule test that refuses a body with a present quote.

### Pitfall 5: a Mail fix that is "accepted" by the suite
**What goes wrong:** the code is merged, and the behaviour on Mail differs.
**Why it happens:** the fakes model the recipe, not Mail.
**How to avoid:** each of FIX-30 to FIX-34 has a row in the acceptance sitting; a Mail write is judged by the resulting message.
**Warning signs:** a plan for a Mail fix with no device step.

### Pitfall 6: a parser change that is "almost equal"
**What goes wrong:** a hand draft reads as the call's own, or an own copy reads `unproven` on every reply.
**Why it happens:** the strip decides which text counts.
**How to avoid:** keep the differential test in the suite (a seeded, smaller run) and the full run in the plan summary.
**Warning signs:** a new pattern literal in `_split_quote`.

### Pitfall 7: the store lock breaks 23 tests at once
**What goes wrong:** the fixture change turns the suite red in 8 files.
**Why it happens:** those tests read a real store today.
**How to avoid:** land the fakes for the 23 tests and the lock in one plan; use the audit plugin before and after.
**Warning signs:** a lock that returns the real path "when it exists".

### Pitfall 8: two lanes edit the same row or the same CHANGELOG lines
**What goes wrong:** rebase conflicts at merge.
**Why it happens:** every Mail fix adds a CHANGELOG line and a facts row.
**How to avoid:** one facts row for each fix (`Activation`, `Confirm`, `Pasteboard`, `Send after insert` for a new code, §7 for the name rule); merge the lanes one after the other.
**Warning signs:** two open PRs that both touch `CHANGELOG.md` under `Unreleased`.

### FIX-34: the exact linear form

```python
# Source: 05.12-proto/split_quote_linear.py (drop_blocks, drop_tags), run 2026-11-20
_BLOCK = re.compile(r"(?is)<(script|style).*?</\1>")   # the old pattern, unchanged
_TAG = re.compile(r"<[^>]+>")                           # the old pattern, unchanged
_OPENER = re.compile(r"(?i)<(script|style)")            # new


def _drop_blocks(chunk: str) -> str:
    """``_BLOCK.sub("", chunk)`` in linear time."""
    out: list[str] = []
    done = at = 0
    dead: set[str] = set()  # captured names with no closing tag from here on
    while (opener := _OPENER.search(chunk, at)) is not None:
        # equal keys differ in ASCII case only, so they have the same closing tags
        key = opener.group(1).lower()
        block = None if key in dead else _BLOCK.match(chunk, opener.start())
        if block is None:
            dead.add(key)
            at = opener.end()
            continue
        out.append(chunk[done : opener.start()])
        done = at = block.end()
    out.append(chunk[done:])
    return "".join(out)


def _drop_tags(chunk: str) -> str:
    """``_TAG.sub(" ", chunk)`` in linear time: no tag ends after the last ``>``."""
    last = chunk.rfind(">") + 1
    return _TAG.sub(" ", chunk[:last]) + chunk[last:]
```

    except (ValueError, KeyError, TypeError):
        return "", ""

### Applicable ASVS Categories

| ASVS category | Applies | Standard control |
|---------------|---------|-----------------|
| V2 Authentication | no | The identity route has no login; the socket's file mode is the gate |
| V3 Session Management | no | — |
| V4 Access Control | yes | The unix socket is `0600` in a `0700` folder (`daemon.bind_socket`); the dispatcher serves MCP routes on that socket only; the route returns what `doctor` already returns |
| V5 Input Validation | yes | Stored mail is untrusted input: linear parse, a size cap, a fixed code for each refusal. The identity answer is untrusted for `launch`: a bad answer means "restart", never a crash |
| V6 Cryptography | no | Nothing is added or changed |
| V7 Errors and Logging | yes | A refusal text holds no mail text, no clipboard content and no signature; a reason code is one of a fixed set |

### Known Threat Patterns

| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Crafted mail HTML holds the one native worker for minutes (FIX-34) | Denial of service | The exact linear form, the cap, a timed test |
| A name that resolves to another bundle receives the script's events (FIX-30) | Spoofing | Address every app by bundle id; `doctor` probes by id |
| A late key event edits another compose window (FIX-33) | Tampering | An emptied pasteboard through the rollback and the drain wait; the residual is recorded |
| The owner's signature passes for Mail's quote, and a reply goes out without the quote (FIX-32) | Tampering | The count rule; the signature is compared and never logged |
| A restart loses a destructive call without a word (FIX-27) | Repudiation | The existing uncertain-outcome answer; no replay |
| A slow start is taken for a failure, and the daemon is killed again (FIX-27) | Denial of service | No kickstart when nothing answers; a bound above the observed start |
| Details of an unreleased fix reach a public file (FIX-28, FIX-29) | Information disclosure | The private fork; ids only in public files; the merge directly before the release |
| A test opens a real store of the developer's Mac (FIX-35) | Information disclosure | The store lock; the audit plugin at 0 rows |
