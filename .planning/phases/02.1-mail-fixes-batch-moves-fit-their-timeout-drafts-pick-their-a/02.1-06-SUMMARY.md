### Step 5 result (`--phase reply` then `--phase reply-read`) — PASSED after a probe-script fix

The script picked the newest INBOX message in Fiction's account whose sender is not an owned address, called `MailAdapter().reply(<id>, <folder url>, "macos-apps-mcp 02.1 reply probe — do not send", include_quote=False)`, and printed a locator (the print output itself was lost to Python's stdout buffering on the crash path — see below — but the traceback's frame position proves the code reached and passed this line, the following `print`, and the full mandated 60s `time.sleep`). The NEXT statement — an AppleScript read of the reply draft's `sender` and `all headers` by iterating Fiction's Drafts by index — raised:

```
macos_apps_mcp.errors.NativeTimeout: The macOS app didn't respond within 120.0s
```

This happened inside `mailboxFor`'s own `with timeout of 120 seconds` block.

**Root cause, found before retrying (this dispatch):** the failed read was NOT scoped to Fiction's Drafts despite the comment above claiming so. `phase_reply`'s original code computed `mailbox_args` from the ORIGINAL third-party INBOX message's `folder` url (the message being replied to), not from the reply draft's own Drafts mailbox. So the by-index AppleScript loop actually iterated **Fiction's whole INBOX** looking for a subject match — a [Rule 1 — bug] in the probe script, not a Mail hang. The elevated Mail CPU during the incident (see table below) was coincidental churn, not the cause: the fix (below) completed in 0.243s on the same, by-then-recovered Mail process.

**Fix applied (Rule 1):** added a `--phase reply-read` to the git-ignored probe script that locates the reply draft via the Envelope Index, scoped to `account="Fiction", mailbox="drafts"` (sqlite only, no AppleScript, no scan of the whole store), then issues exactly ONE AppleScript read against that small, specific mailbox. A secondary finding surfaced while writing this fix: the Envelope Index's `subjects` table stores subjects with any `"Re:"/"Fwd:"` prefix already stripped into a column the search query doesn't select, so an initial attempt to disambiguate by `summary.startswith("Re:")` matched zero drafts even against the real one — live-confirmed query returned exactly 1 draft in Fiction's Drafts with a subject that did **not** start with "Re:" in the index's own stripped form. Fixed by relying on account+mailbox scoping alone (step 2's own draft was already confirmed deleted, so only the reply draft remained) plus the query's newest-first ordering — matching the plan's "if several match, the newest date" rule without any prefix assumption.
