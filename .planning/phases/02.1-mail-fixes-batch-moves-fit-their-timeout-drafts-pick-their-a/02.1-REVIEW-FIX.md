## Fixed Issues

### WR-01: `_scaled_timeout`'s MAX_TARGETS clamp bounds *ids*, not the *copies* a duplicate-heavy batch actually acts on

**Files modified:** `macos_apps_mcp/adapters/mail.py`
**Commit (develop, post rebase-merge):** `5245cb1`
**Applied fix:** Rewrote `_scaled_timeout`'s docstring to state the clamp's
actual guarantee — it bounds the GATE-10-verified cap at 25 **copies**, not
25 Message-IDs. A duplicate-heavy batch whose total stored-copy count exceeds
25 relies on 02.1-01's receipt-on-timeout path, not a wider cap. The formula
(`base + per_id * min(n, MAX_TARGETS)`) is unchanged.

### WR-02: `trash_mail`'s docstrings round the bounded wait up from 5.5s to 6s

**Files modified:** `macos_apps_mcp/server.py`, `macos_apps_mcp/adapters/mail.py`
**Commit (develop, post rebase-merge):** `e3c207e`
**Applied fix:** Replaced "within a bounded 6s wait" (server.py) and the
unquantified "a bounded wait" (mail.py's `_TRASH` comment) with the real
figure: 12 checks, 0.5s apart — 11 gaps, up to 5.5s. The `repeat 12 times` /
`delay 0.5` AppleScript loop is unchanged.

### IN-01: CHANGELOG's `create_draft` dry-run sentence doesn't apply to `create_draft`

**Files modified:** `CHANGELOG.md`
**Commit (develop, post rebase-merge):** `918bf97`
**Applied fix:** Split the MAIL-04 changelog sentence so the "dry run still
makes no native call" guarantee is scoped to `send_mail` only — `create_draft`
has no `dry_run` parameter and now says so explicitly.

### IN-02: `move_mail`/`trash_mail`'s `act()` closures read the destination's before-count even when nothing will act

**Files modified:** `macos_apps_mcp/adapters/mail.py`
**Commit (develop, post rebase-merge):** `3141e42`
**Applied fix:** Extended both empty-`pairs` short-circuit comments (in
`move_mail`'s and `trash_mail`'s `act()` closures) to state that the
destination's before-count already ran by that point — a discarded read, not
a second Apple Event. Code order unchanged, per review scope rule.

### IN-03: `owned_sender`'s `<...>` extraction takes the *last* bracket pair, which is correct but undocumented against adversarial display names

**Files modified:** `macos_apps_mcp/adapters/mail_outgoing.py`
**Commit (develop, post rebase-merge):** `e5259d6`
**Applied fix:** Added a sentence to `owned_sender`'s docstring stating that
taking the LAST `<...>` pair is the deliberately-safe choice, not merely the
Mail-compatible one: a display name that itself contains a `<...>` pair
cannot smuggle a second address past the ownership check.
