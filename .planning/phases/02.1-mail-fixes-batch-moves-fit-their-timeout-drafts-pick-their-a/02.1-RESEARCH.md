## Summary

This phase has **no open design questions** — `02.1-CONTEXT.md` (D-01..D-18) already locks every
behavioral decision from two device spikes (005, 006). What this research adds is the **exact,
re-verified file:line anchors** for every site D-01..D-18 names (several had drifted a few lines
from the context doc's estimates during Phase 02 — corrected below), plus the **mechanical
implementation gaps** the context doc leaves to "Claude's Discretion": the scaled-timeout helper
shape, the `test_applescript_timeout.py` resolver extension needed to tripwire a *computed* host
cap, the missing `NativeTimeout` import in `mail_recover.py`, and the one real subtlety the context
doc doesn't flag — that D-04's bulk-read `_PRESENT` has a cost driven by **mailbox size**, not
batch size, which conflicts with D-02's "every `_PRESENT` call" being folded into the same
`base + per_id × len(ids)` formula as `_MOVE`/`_TRASH`.

**Primary recommendation:** Implement D-01's by-ID act (`proto_act()` in spike 006's
`probe_move.py`, lines 123-165, already proven against real Mail) as the new `_MOVE`/`_TRASH`
bodies; thread a single `scaled_timeout(n) -> float` helper (module-level, baked-in `base`/
`per_id` constants) through every `_MOVE`/`_TRASH`/`_PRESENT` call site so `test_applescript_timeout.py`
can resolve one callable and evaluate it at `mail_recover.MAX_TARGETS` (25) for GATE-10; wrap
`recoverable()`'s `act(located)` call (`mail_recover.py:472`) in a `try/except NativeTimeout` that
writes the `done` record before re-raising with the receipt-specific message; and land the
`from_address` ownership check as a new `mail_addressing` read + a new `mail_outgoing` refusal
helper, called from both `new_message().dispatch` and the new `_CREATE_DRAFT` argv item, never in
either tool's dry-run path.

### Pattern 1: The by-ID act (replaces the per-id `whose` scan)

**What:** Map every target's Message-ID to Mail's internal id with ONE bulk read of the source
mailbox, then address each message as `«class mssg» id n of src` — a reference that resolves in
4-12ms regardless of mailbox size, instead of the `whose message id is mid` scan that costs
0.1-0.25ms **per stored message** (so O(mailbox), not O(1)).

**When to use:** Any destructive batch op scanning a mailbox for a known small set of ids —
`_MOVE`, `_TRASH`. NOT `_DEDUPE`, which has no per-copy handle and must keep `whose` (D-03's
comment-fix at `mail.py:477`).

**Example** (device-proven, spike 006):
```applescript
-- Source: .claude/skills/spike-findings-macos-apps-mcp/sources/006-mail-move-budget/probe_move.py
-- BULK (lines 37-61) — one bulk read maps Message-ID -> internal id, same order:
tell application "Mail"
  set mids to message id of every message of mb
  set nids to id of every message of mb
end tell

-- ACT (lines 63-112) — addresses each target by raw-class reference, verifies before
-- acting, verifies the source reference died after:
repeat with k from 1 to (count of mids)
  set mid to item k of mids
  set n to (item k of nids) as integer
  set m to «class mssg» id n of src
  if (message id of m) is not mid then error "internal id resolved to another message"
  move m to dst
  -- then: get message id of («class mssg» id n of src)  -- must raise -1728
end repeat
```

D-01 requires every by-ID `_MOVE` to **verify the destination as a count increase** from one bulk
read of the destination before the batch and one after — never presence alone (the Archive mailbox
on this Mac has duplicate Message-IDs; presence can't distinguish "this move landed" from
"a pre-existing copy was already there").

### Pattern 2: The scaled-timeout helper (D-02, mechanical gap — not specified in CONTEXT.md)

**What:** `_MOVE`, `_TRASH` and every `_PRESENT` call currently pass either no `timeout=` kwarg
(`_PRESENT`'s three call sites: `mail.py:692`, and the two `_presence()` uses at `:1326`/`:1398`/
`:1524`, plus `dedupe.py:484`'s `adapter.presence(...)` — all default to
`runtime._OSASCRIPT_TIMEOUT = 30.0`, `runtime.py:85`) or a flat constant (`_MOVE_TIMEOUT = 300.0`
at `mail.py:380`, `_TRASH_TIMEOUT = 300.0` at `mail.py:459`). D-02 requires these to become
`base + per_id × len(ids)`, computed in **one helper** — but `tests/test_applescript_timeout.py`'s
`_resolve_host_cap` (lines 147-160) only resolves a `timeout=` keyword that is an `ast.Constant` or
a bare `ast.Name` naming a module attribute; a call expression like `timeout=_move_timeout(len(located))`
raises `_Unresolved` today, which is a FAILING test case (the resolver fails closed on anything it
can't pin down — `test_applescript_timeout.py:198-200`), not a skip.

**Recommended shape** (bakes `base`/`per_id` into the function so the test can call it with just
`n`, never needing to parse which argument expression supplied `n` at the real call site):

```python
# macos_apps_mcp/adapters/mail.py — one helper, reused by _MOVE/_TRASH/_PRESENT call sites
def _move_timeout(n: int) -> float:
    return _MOVE_BASE + _MOVE_PER_ID * n

# call site (inside move_mail's act closure):
def act(located):
    return _parse_statuses(
        runtime.run_osascript(
            _MOVE, *src, *dst, US.join(t.id for t in located),
            timeout=_move_timeout(len(located)),
        )
    )
```

**Required test-infra change** — `test_applescript_timeout.py`'s `_resolve_host_cap` needs a new
branch for `isinstance(value, ast.Call)`: resolve `value.func` via the existing `_resolve_expr`
(already handles a bare `Name` or one-level `mod.NAME` chain, lines 114-127) to get the real
Python callable, then **call it with `mail_recover.MAX_TARGETS` (25)** — the worst case the cap
must cover — rather than trying to statically evaluate whatever expression (`len(located)`, a
literal, …) was passed at the call site. This is the one new idea this research contributes beyond
CONTEXT.md's "Claude's Discretion" note; CONTEXT.md leaves the mechanism open, this is a concrete,
minimal design for it (`[ASSUMED]` — not device-verified, since it is test-infrastructure code with
no native call; verify with `uv run pytest tests/test_applescript_timeout.py -q` once implemented).

**Important nuance for the planner — flag, don't silently resolve:** D-02 groups `_PRESENT` into
the same "scales with batch size" formula as `_MOVE`/`_TRASH`. But D-04 changes `_PRESENT`'s
mechanism to **one bulk read of the source mailbox**, whose cost is driven by **mailbox size**
(0.9s on a 9.5k mailbox, 11.2s on 49.5k, `[CITED: spike 006 primitive-cost table]`), not by how many
ids are being checked (`len(ids)` could be 1 or 25 against the same bulk read). A `base + per_id ×
len(ids)` formula for `_PRESENT` would UNDER-cap a small-batch dry run against a huge mailbox and
OVER-cap nothing — the safe direction — but it is answering the wrong question. The planner should
decide explicitly whether `_PRESENT`'s cap uses the same `len(ids)`-based formula (simpler, always
safe, matches D-02's literal wording) or a `per_id` tuned high enough that `len(ids)=1` still covers
the 49.5k-mailbox bulk-read cost (since `_PRESENT` is now a bulk read regardless of `len(ids)`, the
formula's `per_id` term is not really modeling per-id cost for this one call — it would need `base`
alone to cover the worst-case mailbox size, and `per_id` set to 0 or near it). This is exactly the
"Claude's Discretion: the cap numbers" item CONTEXT.md leaves open, surfaced here with the specific
tension so the plan doesn't silently pick numbers that are safe-but-wrong-reasoning.

### Pattern 3: Receipt-on-timeout (D-06)

**What:** `recoverable()`'s `act(located)` call (`mail_recover.py:472`, exact line:
`statuses = act(located) or {}`) must be wrapped so a `NativeTimeout` raised by
`runtime.run_osascript` (the host-side `subprocess.TimeoutExpired` path, `runtime.py:288-296`,
which raises `NativeTimeout` with the GENERIC "dismiss any stuck prompt" text D-06 forbids
surfacing unchanged) still produces a `done` audit record and a receipt-naming error.

```python
# macos_apps_mcp/adapters/mail_recover.py — recoverable(), around line 472
from ..errors import BatchTooLarge, NativeError, NativeTimeout  # NativeTimeout: NEW import

...
audit_write(plan)
try:
    statuses = act(located) or {}
except NativeTimeout as e:
    done = [replace(t, status="unknown") for t in located]
    audit_write({
        "ts": datetime.now().isoformat(timespec="seconds"),
        "tool": "mail_recover",
        "op": op,
        "phase": "done",
        "receipt": receipt_id,
        "results": {t.id: t.status for t in done},
    })
    raise NativeTimeout(
        f"this {op} timed out after it started acting — receipt {receipt_id!r} was "
        "written with every target's outcome recorded as unknown (osascript was "
        "killed; Mail may still finish the Apple Event in flight). Two safe next "
        "steps: re-run the same batch (ids that already moved report "
        "'not-in-source' and are skipped), or mail_undo(\"" + receipt_id + "\"). "
        "Do not assume anything partially moved or partially stayed."
    ) from e
done = [replace(t, status=statuses.get(t.id, "unknown")) for t in located]
```

Only `NativeTimeout` is caught — `AutomationDenied`/`AppNotRunning` (D-06) mean nothing acted,
so the plan record with no `done` record is already the honest state (a receipt whose `find_receipt`
caller sees `outcomes={}` and — per D-07 below — treats every planned target as possibly-acted,
which is still correct: for AutomationDenied/AppNotRunning this is overly conservative but safe,
and matches today's untouched behavior for those two error classes).

### Pattern 4: Undo replays `unknown` as moved (D-07)

**What:** `undo_plan` (`mail_recover.py:549-585`) already has the filter D-07 needs — it is
written, just needs its default read to include the new D-06 crash-case shape:

```python
# mail_recover.py:579, UNCHANGED by this phase — already correct:
if outcomes.get(t["id"], "ok") == "ok"
```

This line defaults a MISSING outcome (the id isn't a key in the `done` record at all — the crash
case where `act()` never returned, no `done` record was ever written) to `"ok"`, so it already
replays. D-06's new `done` record, once added, explicitly maps every target to `"unknown"` — so
the real change needed is `mail_recover.py:579`'s condition must ALSO treat an explicit
`"unknown"` value the same as a missing key:

```python
if outcomes.get(t["id"], "ok") in ("ok", "unknown")
```

**Verify this is correct before changing it**: today, with no D-06 catch yet, an `"unknown"` value
can only occur per-target (never a whole-batch record) when `act()` returns a dict missing some
ids (`mail_recover.py:473`: `statuses.get(t.id, "unknown")`), e.g. a script bug that answers for
fewer messages than given. The D-06 catch makes `"unknown"` also mean "the whole batch, script
killed mid-flight." Both are the same "we do not know, so assume it moved" semantics D-07's
docstring already states, so folding them into one check is consistent, not a special case.

### Pattern 5: Owned-address refusal (D-08/D-09/D-10/MAIL-04)

**What:** `mail_addressing` gains a new owned-address read (co-located with `_ACCOUNTS`,
`mail_addressing.py:267-285`, and `account_map()`, `:288-334`):

```python
# macos_apps_mcp/adapters/mail_addressing.py — new, beside _ACCOUNTS
# Source script: mail_triage.py:137-150's _MY_ADDRESSES, MOVED not copied.
def owned_addresses() -> dict[str, str]:
    """{lower-cased address: Mail's own spelling}. FAILS CLOSED — an unreadable Mail
    raises, never returns {} (opposite of account_map, which is a label lookup only).
    MAIL-04's refusal must never silently treat "Mail unreachable" as "no addresses
    owned", which would refuse every send."""
    raw = runtime.run_osascript(_MY_ADDRESSES)  # moved from mail_triage.py
    out: dict[str, str] = {}
    for chunk in raw.split(US):
        addr = chunk.strip()
        if addr:
            out[addr.lower()] = addr
    return out
```

`mail_outgoing` gains the refusal helper (beside `MAIL_DEFAULT_SENDER`, `mail_outgoing.py:69`, and
the `set sender` line it must mirror into `_CREATE_DRAFT`, `mail_outgoing.py:165`):

```python
# macos_apps_mcp/adapters/mail_outgoing.py — new, beside MAIL_DEFAULT_SENDER
def owned_sender(from_address: str) -> str:
    """The caller's from_address, verified against an owned account, returned in
    Mail's own spelling for `set sender`. Raises (typed, agent-directed) when no
    account owns it — MAIL-04: Mail silently falls back to the default account on
    an unowned address, which this refuses in Python BEFORE any native write."""
    addr = from_address
    if "<" in addr and addr.endswith(">"):
        addr = addr.rsplit("<", 1)[1][:-1]  # NOT email.utils.parseaddr (facts: it
        # returns ('', '') on Mail's "x@y <X@Y>" shape — a display name with an @
        # and no quotes)
    owned = mail_addressing.owned_addresses()
    spelling = owned.get(addr.strip().lower())
    if spelling is None:
        raise ValueError(
            f"{from_address!r} is not an address any Mail account owns — Mail would "
            "silently send from its default account instead of refusing, so this "
            f"call refuses first. Owned addresses: {sorted(owned.values())}"
        )
    return spelling
```

Called from `new_message().dispatch` (`mail_outgoing.py:660-671`) **before** `_SEND` runs, and only
when `from_address` is truthy — matching D-10's "never in the dry run" rule: `deliver()`
(`mail_outgoing.py:538-548`) only calls `outgoing.dispatch()` when `dry_run=False`, so the check
naturally never runs on a dry run (the dry run's `preview()` reports the requested `from` AS TYPED,
unchecked — this is acceptable because nothing is sent and the refusal only needs to fire before
the native write).

### Anti-Patterns to Avoid
- **Readback-then-rollback as the refusal mechanism (D-10).** In the facts §3c zombie-delete state
  a windowless `delete` silently no-ops and the message autosaves into Drafts anyway — "send it,
  then check and roll back if the sender was wrong" can leave exactly the stray draft the whole
  outbound-dry-run discipline exists to prevent. Refuse in Python, before any `make new outgoing
  message`.
- **`email.utils.parseaddr` on Mail's `sender` string.** Returns `('', '')` on `x@y <X@Y>` — a
  display name containing `@` with no quoting, which Mail produces (facts, mail-sender-reply.md
  item "What to Avoid").
- **Caching the owned-address list across a dry run so the dry run can "pre-check" it.** The spike
  findings doc explicitly leaves this undecided ("Decide the dry-run path in the plan... The spike
  did not decide this"); D-10 resolves it by simply never running the check on a dry run at all —
  do not build a caching layer to make the dry run "more thorough" than D-10 specifies.
- **Treating the by-ID act's "more than one copy in source" case the way spike 006's prototype
  did (refuse).** D-03 overrides the spike: ship code must loop over EVERY copy, not refuse. The
  prototype script in `probe_move.py:139` (`"ERROR more than one copy in source; the by-ID act
  moves one"`) is the SPIKE'S behavior, not the shipped behavior — do not copy that line verbatim.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Parsing Mail's RFC822-shaped `sender` (`Name <addr>`) | A custom regex or `email.utils.parseaddr` | The existing extract-before-last-`<...>`-else-whole-string approach already used informally in this codebase (see Pattern 5) | `parseaddr` is device-proven wrong on this exact shape (facts doc, mail-sender-reply.md) |
| A second AppleScript backstop-vs-host-cap checker | A new test file duplicating GATE-10's formula | Extend `test_applescript_timeout.py`'s existing `_resolve_host_cap`/`_CALL_SITES` machinery | Two copies of "what covers MAX_TARGETS" is the exact class of drift GATE-10 already exists to prevent |
| A retry loop around a timed-out batch | Automatic re-run inside `recoverable()` | D-06's error message naming the two manual next steps (re-run; `mail_undo`) | facts doc §5c: "Never 'fix' this with a retry loop inside the script... retrying belongs at the CLI, where re-running IS the retry and a human is watching" |

**Key insight:** every "don't hand-roll" item here already has a doctrine statement either in
`docs/mail-applescript-facts.md` or in an existing GATE. This phase's job is applying those
doctrines to two new call shapes (a scaled timeout, an owned-address check), not inventing new
ones.

## Common Pitfalls

### Pitfall 1: Trusting the shipped `_DEDUPE` comment after D-03 lands
**What goes wrong:** `mail.py:476-477`'s comment ("no per-copy handle... acting through sqlite is
forbidden") currently justifies `_DEDUPE`'s `whose`-based collection delete. Once `_MOVE`/`_TRASH`
gain a per-copy handle (the raw-class reference), a future reader might assume `_DEDUPE` should too.
**Why it happens:** the by-ID act makes "there is no per-copy handle" locally false for `_MOVE`.
**How to avoid:** D-03 requires correcting the comment, not deleting the constraint — `_DEDUPE`
still can't use the by-ID act because it needs to identify WHICH copy survives, and a raw-class
reference identifies a copy ONLY if you already know its internal id from a bulk read matched
1:1 — which still doesn't solve "which copy is the keeper" (that's a byte-identity decision,
unrelated to addressing).
**Warning signs:** a diff that touches `_DEDUPE`'s `whose`-based act in this phase; MAIL-01/02
scope is `_MOVE`/`_TRASH`/`_PRESENT` only.

### Pitfall 2: Forgetting the `_PRESENT` call site in `dedupe.py`
**What goes wrong:** `dedupe.py:484`'s `adapter.presence(batch, url)` routes through
`_present_ids`/`_PRESENT` exactly like `move_mail`'s dry-run preflight. If the by-ID bulk-read
rewrite only updates the three `_presence()` call sites inside `mail.py` (`:1326`, `:1398`,
`:1524`) and the public `presence()` tool method (`:1447-1460`), the CLI's own call is a FOURTH
consumer of the same `_present_ids` function and inherits the change automatically — but if a
scaled-timeout kwarg is added at the wrong layer (inside `_present_ids` itself vs. at each
caller), verify `dedupe.py`'s CLI-scale calls (hundreds of ids, not capped at 25) still get a
sane cap: `_present_ids` has NO `MAX_TARGETS` check (only `mail_recover.check_batch` does, and
`presence()`/`dedupe.py` never call `check_batch`). A per-id scaled formula applied to a
non-25-capped caller could compute an enormous timeout.
**Why it happens:** `_present_ids` is the single shared function (`mail.py:687-692`) — correct
by design — but D-02's "scales with batch size" language was written with the 25-cap in mind.
**How to avoid:** confirm whether the scaled formula should clamp at `MAX_TARGETS` regardless of
actual `len(ids)` (since `_PRESENT` is a bulk read now, its cost doesn't scale with `len(ids)`
anyway — see Pattern 2's nuance) rather than literally multiplying `per_id × len(ids)` for a
CLI call with hundreds of ids.
**Warning signs:** a `dedupe-mail` CLI run that waits minutes longer than expected on its
presence preflight.

### Pitfall 3: `_MOVE_TIMEOUT`/`_TRASH_TIMEOUT` as module-level constants vs. functions
**What goes wrong:** `tests/test_mail.py:1789` asserts `seen["timeout"] == mail._MOVE_TIMEOUT` —
if `_MOVE_TIMEOUT` becomes a function (`_move_timeout(n)`) rather than staying a constant, this
exact test line breaks and must be rewritten as `seen["timeout"] == mail._move_timeout(1)` (the
test's batch is 1 message, `MailAdapter().move_mail("a@x", ...)`).
**Why it happens:** the existing name `_MOVE_TIMEOUT` reads like a constant; D-02 needs a formula.
**How to avoid:** either keep `_MOVE_TIMEOUT`/`_TRASH_TIMEOUT` as the BASE constants (`base`) and
name the new callable something distinct (`_move_timeout`, `_trash_timeout`) so existing constant
references don't silently become stale, or rewrite `test_mail.py:1789` deliberately as part of
this phase's diff (D-01's "reversibility: costly" note already flags "about 29 unit-test fakes...
change").
**Warning signs:** `test_mail.py:1789` failing with a `TypeError` (comparing a float to a function
object) rather than an assertion-mismatch — a sign the rename wasn't threaded through.

### Pitfall 4: The `_ORIGINAL` read's existing 120s backstop is a ceiling, not a target
**What goes wrong:** D-13 says "If the read still times out at 120s on device, the finding goes
to #230 and the xfail stays." Passing `timeout=120.0` matches the script's own `with timeout of
120 seconds` (`mail_outgoing.py:389`) EXACTLY — not comfortably under it. If `quoted_body`'s
caller-side timeout needs to be strictly LESS than the script backstop (so the host-side Python
timeout fires first and gives a clean `NativeTimeout` instead of racing the AppleScript's own
self-abort), equal values could occasionally race.
**Why it happens:** GATE-10's invariant is `backstop >= host cap` (non-strict), so `120.0 ==
120.0` passes the tripwire — but "passes the tripwire" and "doesn't race in practice" are
different claims.
**How to avoid:** this is a `[ASSUMED]` risk, not device-verified; flag it to the planner as worth
a one-line comment in code rather than silently accepting equality, or verify on device during
D-15/D-16's session that the host-side timeout does fire cleanly at 120s (not get raced by the
AppleScript backstop).
**Warning signs:** an occasional non-`NativeTimeout` native error on a slow `quoted_body` read
instead of a clean, agent-directed timeout message.

### GATE-10 tripwire extension for a computed host cap (D-02's open mechanism)

```python
# tests/test_applescript_timeout.py — _resolve_host_cap, new branch
from macos_apps_mcp.adapters import mail_recover as _mail_recover_mod

def _resolve_host_cap(call: ast.Call, module) -> float:
    for kw in call.keywords:
        if kw.arg != "timeout":
            continue
        value = kw.value
        if isinstance(value, ast.Constant) and isinstance(value.value, (int, float)):
            return float(value.value)
        if isinstance(value, ast.Name):
            resolved = _resolve_expr(value, module)
            if not isinstance(resolved, (int, float)):
                raise _Unresolved(f"timeout= resolved to non-numeric {resolved!r}")
            return float(resolved)
        if isinstance(value, ast.Call):
            fn = _resolve_expr(value.func, module)
            if not callable(fn):
                raise _Unresolved(f"timeout= call target {fn!r} is not callable")
            # Evaluate at the worst case the cap must cover, not the call site's own
            # expression (e.g. len(located)) — GATE-10 asks "does the backstop cover
            # MAX_TARGETS", not "does it cover whatever this particular call passed".
            result = fn(_mail_recover_mod.MAX_TARGETS)
            if not isinstance(result, (int, float)):
                raise _Unresolved(f"timeout= call returned non-numeric {result!r}")
            return float(result)
        raise _Unresolved(f"unsupported timeout= expression shape: {ast.dump(value)}")
    return float(runtime._OSASCRIPT_TIMEOUT)
```

## Open Questions

1. **Does the scaled-timeout formula for `_PRESENT` use `len(ids)` or clamp at `MAX_TARGETS`
   regardless of caller?**
   - What we know: `_PRESENT`'s real cost (post D-04) is one bulk read of the source mailbox,
     independent of how many ids are being checked; `dedupe.py:484` calls `presence()` with
     batches far larger than 25 (uncapped — no `check_batch` call in that path).
   - What's unclear: whether D-02's "every `_PRESENT` call" language intends the SAME `len(ids)`-
     scaled formula as `_MOVE`/`_TRASH`, or a mailbox-size-driven cap.
   - Recommendation: the planner should pick ONE formula and document which — using `base` alone
     (no `per_id` term, or a very small one) for `_PRESENT`'s bulk-read-driven cost is the
     reasoning-correct choice; it is also automatically the safe direction for `dedupe.py`'s
     uncapped batches.

2. **Does `quoted_body`'s `timeout=120.0` need to be strictly less than its script's 120s
   backstop?**
   - What we know: GATE-10's tripwire only requires `backstop >= host cap` (non-strict).
   - What's unclear: whether equality can race in practice (host-side `subprocess.TimeoutExpired`
     firing at the same moment the AppleScript's own `with timeout` self-aborts).
   - Recommendation: device-verify during the D-15/D-16 session, or set `timeout=119.0`/similar
     defensively if device time allows a quick check.
