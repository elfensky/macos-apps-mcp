## Warnings

### WR-01: `_scaled_timeout`'s MAX_TARGETS clamp bounds *ids*, not the *copies* a duplicate-heavy batch actually acts on

**File:** `macos_apps_mcp/adapters/mail.py:359-369`
**Issue:** `_scaled_timeout(n, *, base, per_id)` clamps with
`min(n, mail_recover.MAX_TARGETS)`, and its docstring claims this makes the GATE-10
check "true for every `n` a caller could ever pass." `check_batch` does cap the
number of **Message-IDs** (`mids`) at 25 before any native call
(`mail.py:1535`/`1662`), but the host cap passed to `_MOVE`/`_TRASH` is computed from
`len(pairs)` (`mail.py:1581`, `1707`), where `pairs` is one entry **per stored copy**
of each Message-ID (D-03: a duplicated Message-ID gets every copy acted on). A batch
of 25 Message-IDs each with 2 copies in the source produces `len(pairs) == 50`, and
the clamp caps the host timeout at the same 435s ceiling as a 25-copy batch — roughly
half the time a 50-event Apple Event batch needs. The resulting behavior is safe
(`recoverable()`'s `NativeTimeout` catch writes a receipt and reports the two safe
next steps, D-06/D-07), so this is not a data-loss risk, but the docstring's "every
`n`" claim is not accurate, and a duplicate-heavy real mailbox (#153's own census
found cross-account duplicate sets) makes a spurious timeout on a legitimately-sized
batch more likely than the formula's sizing rationale (D-02's comment, keyed only off
`MAX_TARGETS`-many *messages*) suggests.
**Fix:** Either clamp on the true worst case (`MAX_TARGETS * <some bound on copies
per id>`) or rewrite the docstring/comment to state the clamp's actual guarantee
("bounds the GATE-10-verified cap at 25 **copies**; a batch whose total copy count
exceeds 25 relies on the timeout-receipt path, not a wider cap") so a future reader
does not treat "25 ids at the batch cap" as "this can never run long."

### WR-02: `trash_mail`'s docstrings round the bounded wait up from 5.5s to 6s

**File:** `macos_apps_mcp/server.py:807` (also `macos_apps_mcp/adapters/mail.py:600`)
**Issue:** `_TRASH`'s post-delete probe (`mail.py:659-678`) is `repeat 12 times` with
`delay 0.5` **after** each failed check, so the loop performs 12 checks separated by
11 half-second delays — a maximum of 5.5s of added wait, not 6s. The tool docstring
says "within a bounded 6s wait," which is close enough to mislead a future change
(e.g., "round the loop to 10 iterations, nothing changes" would actually cut the wait
to 4.5s against a docstring still claiming 6s).
**Fix:** Say "11 × 0.5s ≈ 5.5s" or simply "a bounded multi-second wait" to avoid a
number that doesn't match the loop shape.

## Info

### IN-01: CHANGELOG's `create_draft` dry-run sentence doesn't apply to `create_draft`

**File:** `CHANGELOG.md:18-20`
**Issue:** "`send_mail` and `create_draft` refuse a `from_address` no Mail account
owns (MAIL-04, #208) — before, Mail silently sent from its default account; the dry
run still makes no native call." `create_draft` has no `dry_run` parameter at all —
it always performs the native write (`server.py`'s `create_draft` signature, and
`mail_drafts.create_draft`). The sentence reads as if both tools have a dry-run mode
whose "no native call" guarantee is preserved; only `send_mail` does.
**Fix:** Split the sentence: "`send_mail` and `create_draft` refuse a `from_address`
no Mail account owns … `send_mail`'s dry run still makes no native call."

### IN-02: `move_mail`/`trash_mail`'s `act()` closures read the destination's before-count even when nothing will act

**File:** `macos_apps_mcp/adapters/mail.py:1569`, `1695`
**Issue:** `before = _counts(dst)` runs unconditionally, before the `if not pairs:
return {...}` short-circuit that applies when every requested id turned out to have
no copies in the source. That short-circuit exists precisely to avoid "no `_MOVE` call,
no second count" (the comment at `mail.py:1572-1573` and its mirror at `1697-1699`
promise this), but the destination's bulk read already happened by the time the
check runs, so the promise is half-kept: the `_MOVE`/`_TRASH` Apple Event is skipped,
but the destination `_BULK` read is not. Functionally harmless (a discarded read), but
worth moving after the `pairs` check so the comment's claim is accurate and the no-op
path truly issues zero extra Apple Events.
**Fix:** Compute `pairs` (or at least check whether `copies` has any non-empty values)
before calling `_counts(dst)`, and skip the destination read entirely on a fully
empty batch.

### IN-03: `owned_sender`'s `<...>` extraction takes the *last* bracket pair, which is correct but undocumented against adversarial display names

**File:** `macos_apps_mcp/adapters/mail_outgoing.py:90-92`
**Issue:** `addr.rsplit("<", 1)[1][:-1].strip()` is right for Mail's own `x@y <X@Y>`
shape (the stated reason), and also happens to do the right thing for a malicious
display name containing an embedded `<...>` (e.g. `"A<fake@x> <real@y>"` resolves to
`real@y`, the last pair) — but this is incidental, not stated, and the function's
docstring only explains the Mail-shape case. Since this value feeds directly into an
ownership check that gates an outbound write, a one-line note on why "last pair wins"
is the deliberately-safe choice (not merely the Mail-compatible one) would save the
next reader from re-deriving it.
**Fix:** Add a sentence to the docstring: "the LAST `<...>` pair, so a display name
that itself contains one cannot smuggle a second address past the match."
