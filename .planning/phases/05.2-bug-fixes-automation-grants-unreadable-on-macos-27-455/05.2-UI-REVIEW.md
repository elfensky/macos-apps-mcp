## Plain summary

The page is a row of indicator lights for the permissions the server needs. The phase made the lights honest: a light that cannot be read is grey and says why, and it no longer points to a settings pane that cannot help. The remaining faults are small. Grey means three different things. One amber light still has a button that leads to an empty pane. Two grey lights do not say what to do next. Today the effect is a moment of confusion for the operator. Nothing blocks a task, and no state is reported falsely.

---

## Top 3 Priority Fixes

1. **`Open Settings` on the "Not asked yet" row cannot help** (`macos_apps_mcp/dashboard/health.py:327`) — macOS lists an app in the Automation pane only after the app was asked, so the button opens a pane with no switch for it. `tests/test_dashboard_system.py:424` records the same fact (PM-13). The 05.2-04 truth and the sketch rule require the button "when on", so the fix is a contract change: show the action only for `denied`, and keep the text instruction for `not asked`.
2. **The Accessibility error row is a dead end** (`macos_apps_mcp/dashboard/health.py:172-173`) — the row reads "Could not be read" and nothing else. `doctor` returns a remediation for `probe_error` ("…mail_reply and reply_all may refuse", `macos_apps_mcp/doctor.py:323-324`), and the row drops it. The 05.1 rule says a failure state leads somewhere. The fix is to show `s.get("remediation")` as the sub when it is present, with "Could not be read" as the fallback.
3. **One grey dot has three meanings** (`macos_apps_mcp/dashboard/health.py:167-169`, `173`, `331-337`, `340-347`) — "the adapter is off, so this does not matter", "cannot be told until the app is running" and "the check failed" look the same. A failed check is the only one of the three that is a possible problem. The fix is the accent dot (`warn`) for the two "Could not be read" rows; it needs no new token. This also needs a contract line, because 05.2-12 says "grey when the check failed".

## Detailed Findings

### Pillar 1: Copywriting (3/4)

Met:

- The not-running row says what is unknown and why, and names the action: "Cannot be told until the app is running: Contacts. Open the app, then reload this page." (`health.py:335-336`). It has no "System Settings" text, as the 05.2-04 prohibition requires.
- The not-asked row names the real first step (`doctor(request=True)`), not the pane (`health.py:317-318`).
- The Accessibility remediation carries the macOS 27 pane name: "Device Control and Data Access (called Accessibility before macOS 27)". It comes from `doctor`, so both surfaces agree.
- A partial or failed TCC read never claims "not asked" (`health.py:309-311`).

Findings:

- WARNING (defect) — `health.py:358-361`: the macOS 27 note says "Calendar and Reminders grants cannot be read here", and the next sentence says the EventKit row comes from a live check. The EventKit row is the Calendar and Reminders grants, and it shows "full access" directly below. The note should say that the grant database cannot be read and that every row below comes from a live check. The 05.2-04 truth pins the substring "cannot be read here"; the truth and its test change with the text.
- WARNING (defect) — `health.py:172-173`: see priority fix 2.
- WARNING (nit) — `health.py:335-336`: "Open the app" is singular after a list of up to five apps. "Open each app" is correct for both cases.
- WARNING (nit) — `health.py:317`: "run doctor(request=True)" does not say where. The operator is on a web page; the call is an MCP tool. "ask your MCP client to run doctor(request=True)" removes the doubt.
- WARNING (nit) — `health.py:325`: the arrow in "Automation → Notes" is read by a screen reader as "right arrow". The sketch fixes this title, so this is a note only.

### Pillar 2: Visuals (3/4)

Met: the rows keep the sketch 004 structure (dot, title, sub, action at the right). The Accessibility row sits directly after Full Disk Access. The danger banner is the focal point when an active adapter is denied.

Findings:

- WARNING (defect) — one grey dot, three meanings: see priority fix 3.
- WARNING (nit) — `health.py:301`: the `Automation → {App}` rows follow `grants.ADAPTER_GRANTS` order, so an amber "Not asked yet" row can stand above a red "Denied" row (capture `desktop.png`: Music above Notes). Denied rows should come first.
- WARNING (nit) — `dashboard.css:353` with `dashboard.css:270`: the macOS 27 note has a 12 px side margin and the same 760 px maximum width as the group, so at 1440 px its right edge stands 12 px outside the group (capture `desktop.png`). Older code, but this phase lengthened the text to two lines and made the overhang visible.
- WARNING (nit) — `health.py:312`: a granted Automation grant has no row, while Full Disk Access and Accessibility show "Granted" with a green dot. The contract asks for this ("one row per grant that is not granted"). The effect is that absence means "good", and the operator cannot tell it from "not checked". One summary row ("Automation: granted for N apps") would close the gap.

### Pillar 3: Color (3/4)

Met:

- Phase 05.2 added no token and no CSS rule. The last change to `dashboard.css` is from Phase 05.1 (2026-10-24). `health.py` holds no colour value.
- Dot glyphs on the surface, light and dark: ok 6.06 and 6.89, warn 5.97 and 6.78, bad 6.39 and 5.03, grey 3.67 and 4.27. All are above the 3:1 glyph floor of 05.1.
- Row sub text: 5.54 (light) and 6.30 (dark). The note text on the page background: 5.09 and 7.54. All are above 4.5:1.
- No state is carried by colour alone: each row states it in text ("Granted", "Denied", "Not asked yet", "Could not be read").

Findings:

- WARNING (nit) — `health.py:111` with `dashboard.css:121` and `153-158`: `Open Settings` is an `<a class="btn">`, and `.btn` sets no colour, so the label is link blue: 4.02:1 on the light surface and 3.82:1 on the dark surface. `05.1-03-PLAN.md:111` records the link blue at 4.02:1 as a default taken, so the light value is a known exception; the dark value is lower than the recorded one. Sketch 004 draws this control as a push button with the text colour, like `Copy`. `a.btn { color: var(--color-text); }` meets 4.5:1 in both themes and matches the sketch. This phase raised the count of these buttons on one page from two to as many as nine.
- Older code, note only: the "●" glyph of the danger banner has the text colour, not the danger colour. The tinted background carries the severity.

### Pillar 4: Typography (4/4)

Met: titles use `--text-base` (13 px), subs and the note use `--text-sm` (12 px), both at the regular weight; the banner lead is bold. No raw pixel size was added.

Findings:

- WARNING (nit) — `health.py:317`: `doctor(request=True)` is a literal call in plain text. The page lede sets `doctor` in `.mono` (`health.py:458`). `_row` escapes the sub as plain text, so this needs a `Safe` sub.

### Pillar 5: Spacing (3/4)

Met: no new spacing value. The rows wrap and nothing overflows at 375 px or 768 px (captures `mobile.png`, `tablet.png`, `mobile-dark.png`).

Findings:

- WARNING (defect) — `dashboard.css:404-406` with the phone block at `dashboard.css:307-317`: a row with an action keeps the button on the same line at every width. At 375 px the text column is about 180 px wide. The Accessibility remediation wraps to seven lines and the "Not asked yet" text to four (capture `mobile.png`). A phone rule that lets `.health .row` wrap and puts the button under the text is the fix. The texts added by this phase are the longest on the page, so this phase made the squeeze visible.
- WARNING (nit) — `dashboard.css:155`: `.btn` has `min-height: 24px` and no phone override, while the phone block gives nav items 44 px and the switch a larger hit area (`dashboard.css:312`, `314`). 24 px meets the WCAG 2.2 AA minimum; it does not meet the 44 px rule that 05.1 applied to the other controls.

### Pillar 6: Experience Design (3/4)

State coverage, met and tested:

| State | Row | Evidence |
|-------|-----|----------|
| Live granted | no row | `test_live_granted_automation_needs_no_tcc_row` |
| Live denied, adapter on | red dot, "Denied", `Open Settings`, banner, sidebar dot | `test_live_denied_automation_is_a_row_and_a_banner_entry` |
| Live not asked, adapter on | amber dot, "Not asked yet…" | `test_live_not_asked_automation_has_an_accent_dot` |
| App not running | one grey row, no Settings button | `test_not_running_automation_says_the_state_cannot_be_told` |
| Probe error, TCC silent | grey "Could not be read for …" with the pane name | `test_an_unreadable_tcc_database_says_so_and_never_claims_not_asked` |
| Adapter off | grey, "does not matter", no action, no banner | `test_an_off_adapter_raises_no_banner_and_says_it_does_not_matter` |
| Accessibility: granted, not granted, Mail off, check failed | four rows, no banner, no sidebar change | `test_health_shows_the_accessibility_grant`, `test_accessibility_row_raises_no_banner` |
| Worker busy, `doctor` failed | busy row and note, or a danger banner; never a stale grant | `test_health_busy_and_single_flight` |

Findings:

- WARNING (defect) — `health.py:327`: an action that cannot help. See priority fix 1.
- WARNING (defect) — `health.py:172-173`: a dead-end error row. See priority fix 2.
- WARNING (defect, accessibility) — `health.py:111`: every action has the same accessible name, "Open Settings", with up to three different targets. In a screen reader's link list the entries cannot be told apart. `_settings` should take the row title and set `aria-label="Open Settings: {title}"`.
- WARNING (nit) — `health.py:331-337`: the grey row says "reload this page" and offers no control for it. A `Reload` link (`<a class="btn" href="/health">`) is an action that can help, and it works without JS.
- WARNING (defect, accessibility, older code) — `macos_apps_mcp/dashboard/html.py:96`: the Health dot in the sidebar is an empty `<span>` with no text. A screen reader says "Health" and no state. This phase changed what the dot reports (a live denial now turns it red), so the silent state matters more. A visually hidden text (`.sr` exists at `dashboard.css:127`) such as "problem", "restart pending" or "ok" is the fix.
- WARNING (nit, accessibility, older code) — `health.py:77-87`: the rows are `<div>` elements with no list role, so a screen reader cannot announce the row count or let the user move by item. The row dots have no text, which is acceptable here because each sub states the status in words.
- Not checked: the `x-apple.systempreferences:` links on a device, the focus ring on the new buttons in a real browser, and the page under a real busy worker. These need the installed daemon, which this audit did not use.

Registry audit: not applicable. `components.json` does not exist and the contract names no third-party registry.
