## Warnings

### WR-01: dark contrast is measured on one of the two dark blocks

**File:** `tests/test_dashboard_contrast.py:120-127` (fixture `dark`), `:34` (`DARK_OPENERS`)
**Issue:** The `dark` fixture overlays only `:root[data-theme="dark"] {`. The block a normal
macOS user gets, `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {`, is only
checked for *presence* of the four `*-text` tokens (`test_dark_mode_declares_every_text_token`),
never for value. The two blocks are hand-duplicated in the CSS. If a later edit changes
`--color-text-muted`, `--color-text-faint` or a `*-text` token in one block only, every dark
measurement stays green while OS-dark users render a failing pair. This is exactly the PM-02/PM-03
failure class (declared but not measured) that #441 set out to close, re-opened for the second block.
I confirmed that the two blocks are equal today, so this is a test gap, not a live defect.
**Fix:** Add one assertion that the two dark token dicts are equal, or run the dark parametrised
tests over both openers.

```python
def test_both_dark_blocks_declare_the_same_tokens(css):
    a, b = (_tokens(css, o) for o in DARK_OPENERS)
    assert a == b
```

### WR-02: light-mode text pairs below 4.5:1 remain, and the CHANGELOG says text is measured at 4.5:1

**File:** `macos_apps_mcp/dashboard/dashboard.css:217` (`.nav-item .count`), `:216`
(`.nav-item.active`), `CHANGELOG.md` (#428 entry)
**Issue:** This is PM-04 and PM-16, still open at HEAD. I recomputed with the test's own maths.
- Light `--color-text-muted` on `--color-selection` over the sidebar is 3.94:1. That is the
  `.nav-item.active .count` text, at `--text-xs`, so the normal 4.5:1 threshold applies.
- The same colour over the page background is 4.38:1. That is the muted `.sub` line of a selected
  write row.

PM-04's disposition said "deferred to 05.1-06 (same CSS)". The 05.1-06 SUMMARY (line 103) says the PM-04 and
PM-16 rules were "not touched". So the deferral was dropped without a decision. The CHANGELOG #428
entry says chip, word-diff and status-dot colours are "measured at 4.5:1 for text and 3:1 for glyphs
in light mode". The tests only cover the three pairs that pass (the code comment above `LIGHT_CHIP_PAIRS`
names the two that fail). A reader of the CHANGELOG gets a stronger claim than the code supports.
**Fix:** Take PM-04's smallest fix and cover the other pair, then pin both in `LIGHT_CHIP_PAIRS`:

```css
.nav-item.active .count { color: var(--color-text); }   /* PM-04 */
.row.selected .sub { color: var(--color-text); }         /* PM-16: or darken muted until 4.5:1 holds */
```

If the owner prefers to accept them, say so in the CHANGELOG ("except muted text inside a selected row")
and record the acceptance next to PM-04/PM-16 so the deferral has an owner.

## Info

### IN-01: a lost-audit banner is process-wide, short-lived and cleared by the next good write

**File:** `macos_apps_mcp/dashboard/adapters.py:29-36, 290`
**Issue:** `_audit_lost = not ok` is overwritten by the next write, so a lost toggle record stops
being reported the moment a later toggle succeeds, although the earlier record is still missing from
`audit.jsonl`. A lost *restart* record shows on the restarting page only; the new daemon process starts
with `_audit_lost = False`. This matches owner default O3 (it is the planned behaviour), so it is INFO.
**Fix:** If the owner wants the signal to persist, keep a sticky flag or a list of lost ops until the
process ends, and name the op in `_LOST_NOTE`.

### IN-02: the Restart record means "requested", and a failed render leaves a record for a restart that never ran

**File:** `macos_apps_mcp/dashboard/adapters.py:362-368`
**Issue:** The planned change (05.1-07 "planner choice") moved the record before the response.
`restart_logged` is set before `_render(...)` runs and before the hook is scheduled as a background task.
If `_render` raises (for example `deploy.grant_report` or `audit.usage_read` fails), the audit log says
"Restarted the daemon", no restart happened, and a retry writes no second record (flag already set) and
no corrective record. The pre-phase code logged only when `hook()` returned True (the restart was armed).
**Fix:** Wrap the render so that a failure resets the flag, or log a `restart_failed` record, or render
first and only then log and schedule the hook.

### IN-03: the `not built` text keeps 30 characters and drops the exception type

**File:** `macos_apps_mcp/daemon.py:352`
**Issue:** `sanitize_line(str(e) or type(e).__name__)[:NOT_BUILT_MAX]` shows the type name only when the
message is empty. A `KeyError` or `OSError` is cut to 30 characters of message text with no class and no
pointer to the log (where `exc_info=True` holds the traceback). A whitespace-only message gives
`not built: ` (empty after `sanitize_line`, and the `or` does not fire because `str(e)` is non-empty).
The 30-character cap is tuned to a doctor budget test with one character of headroom (6999 of 7000, see
PM-09 evidence), so the next unrelated doctor field fails that test and invites raising the cap.
**Fix:** `msg = sanitize_line(f"{type(e).__name__}: {e}" if str(e).strip() else type(e).__name__)[:NOT_BUILT_MAX]`,
and end the state with a log hint if the budget allows. Consider budgeting from `NOT_BUILT_MAX` in the test
instead of a literal 7000.

### IN-04: `not bound` state is still unsanitised

**File:** `macos_apps_mcp/daemon.py:334`
**Issue:** `dashboard_state = f"not bound: {e}"` takes the raw `OSError` text. PM-10 closed this hole for
`not built` only. An `OSError` from `bind` is short in practice, so the risk is the inconsistent rule
("one sanitised line") rather than a live bug.
**Fix:** Apply the same `sanitize_line(...)[:NOT_BUILT_MAX]` to `str(e)`.

### IN-05: label coverage depends on a warm Mail account cache, and a dashboard Restart empties it

**File:** `macos_apps_mcp/adapters/mail_addressing.py:439-461`, `CHANGELOG.md` (#427 entry)
**Issue:** The CHANGELOG states the limit (the page shows the raw URL until a Mail tool has filled the
map). Worth recording: the dashboard's own Restart button is the commonest cause of a cold cache. So the
page that shows `imap://` URLs most often is the one right after the operator restarted the daemon.
Also, `refresh_account_map` sets the cache to `None` for the length of an osascript call, and the dashboard
shows raw URLs in that window. Both are by design (D-09: a page never starts Mail).
**Fix:** None required. If it proves annoying at UAT, persist the uuid-to-name map in the daemon state dir
when `account_map()` fills it and read that file in `cached_account_names()`.

### IN-06: CHANGELOG claim "the daemon reads its adapter deny-list once per start" is too broad

**File:** `CHANGELOG.md` (#430 entry), `macos_apps_mcp/server.py:46`
**Issue:** Only tool *registration* uses the import-time snapshot. `registry.adapter_status()`,
`registry.outbound_status()`, `doctor` (lines 129, 173, 200) and `eventkit.request_access_each` (PM-13) read
the file again per call, on purpose. A reader may think a mid-run edit of `adapters_off` is invisible to the
daemon.
**Fix:** "registers its tools from one read of the adapter deny-list per start".
