## Warnings

### WR-01: Contacts search lost its in-AppleScript cap, so a broad query reads every person five times

**File:** `macos_apps_mcp/adapters/contacts.py:46-63`
**Issue:** The old loop stopped at `maxN`, and its comment said that is the point: a broad query ("a") must not fetch phone and email for thousands of people just to drop all but 50. The new script materialises `id`, `name`, `organization`, `value of phones` and `value of emails` for the entire match set (five whole-set reads, each a full `whose` scan). It applies `maxN` only afterwards, in `if howMany > maxN then set howMany to maxN`. The measured 9 s is for 52 matches of 192 people. On a real address book with thousands of matches, a one-letter query runs five full scans plus all the nested phone and email reads. It can hit the `with timeout of 120 seconds` limit and fail with `NativeTimeout` (-1712) where the old code returned 50 rows. The reply is still capped, so only the work is unbounded. This reverses a documented guarantee, and the new header comment does not mention the trade-off.
**Fix:** Bound the reads without losing the one-event-per-property form. Read `id` and `name` first (cheap scalar reads), and trim to `maxN` indexes. Then fetch phones and emails only for the kept people through id-based specifiers, for example `value of phones of (people whose id is in keptIds)`. Alternatively, accept the cost and state it in the comment. Add a note in the tool docstring that a broad query on a large book can time out, and have the adapter report truncation, since a 50-row answer is currently indistinguishable from an exact 50.

### WR-02: "(account not in Mail)" is a false claim when the cached account map is stale

**File:** `macos_apps_mcp/adapters/mail.py:2370` (map source: `macos_apps_mcp/adapters/mail_addressing.py:305-334`)
**Issue:** `names.get(uuid) or (UNNAMED_ACCOUNT if names else uuid)` treats any uuid absent from a non-empty map as "Mail does not list this account". `account_map()` caches a non-empty success forever, for the life of the daemon. The daemon is long-lived. An account added to Mail after the first overview call is therefore labelled "(account not in Mail)" until the daemon restarts, although Mail does list it. Before this change the raw uuid was shown, which was honest. The label also covers an account that Mail returns with an empty name, because `""` is falsy and shows the same label. The tool docstring says the label means "Mail answers but does not list" the account. For both of these cases that statement is wrong.
**Fix:** Before concluding "not in Mail", retry once with a fresh read. Either bypass or invalidate the cache for the missing uuid (a one-shot `_ACCOUNT_MAP_CACHE = None; names = account_map()` when a non-local uuid is missing), or give non-empty successes a long TTL like failures. Show the uuid, not the label, for an empty-named account.

## Info

### IN-01: The contacts alignment guard is pinned by a substring test only

**File:** `tests/test_contacts.py:197-201` (also `:190-191`)
**Issue:** `test_contacts_search_bulk_lists_must_stay_aligned` asserts only that the text `"changed during the read"` occurs in `_SEARCH`. It would still pass if the `count of` comparisons were deleted or wrong. `test_contacts_search_end_to_end_bulk_form` likewise checks script substrings. The unit suite cannot run AppleScript, so these are cheap guards at best. They give the review a false sense that the pairing logic is covered. The guard also compares counts only. If one contact is deleted and another added between the five reads, the counts match and fields from different people are paired.
**Fix:** Mark the real check as integration (a `-m integration` test that calls `_SEARCH` on the device with a known-multi-phone contact). Rename the substring tests so they do not claim to test alignment. Optionally compare the id list to a second `id of (people whose ...)` read taken after the property reads, and error if they differ.

### IN-02: Shim client factory swallows every exception, not only the two documented paths

**File:** `macos_apps_mcp/daemon.py:268-274`
**Issue:** The docstring names two fallback paths: `initialize` (`client_params` is `None`, so `AttributeError`) and `ping` (`get_context()` raises `RuntimeError`). The code catches `Exception`. A future fastmcp or mcp change that renames `session` or `clientInfo` would silently collapse every audit record to `macos-apps-mcp-shim 0`, and no log line would show it. The audit trail would degrade without any signal. `audit._caller` does it correctly with `(AttributeError, RuntimeError)`.
**Fix:** `except (AttributeError, RuntimeError):`. Keep the `# noqa` out. If the broad catch is deliberate, log once at debug level on the fallback.
