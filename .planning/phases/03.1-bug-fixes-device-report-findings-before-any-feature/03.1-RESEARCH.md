### Locked Decisions

#### Audit record: resolved dry_run and caller (FIX-01, #222)
- **D-01:** `AuditMiddleware` resolves `dry_run` for each call from the tool's signature default.
  A new registry view `registry.dry_run_defaults()` (next to `audit_verbs()`, derived from
  `inspect.signature(rec.fn).parameters.get("dry_run")`) gives the defaults to the middleware at
  construction, the same way `audit_verbs` is given. `args` stay exactly as the client sent them.
  The envelope gets two new top-level keys: `dry_run` and `caller`. No tool body changes.
- **D-02:** Every middleware record carries a boolean `dry_run`. Eleven tools default to `true`:
  `delete_draft`, `move_mail`, `trash_mail`, `mail_undo`, `send_mail`, `reply_all`,
  `forward_mail`, `delete_reminder`, `delete_event`, `delete_note`, `update_note`.
  `update_mail_status` and `run_shortcut` default to `false`. A tool with no `dry_run` parameter
  always acts and records `false`. Previews stay in the log and `op` keeps its verb (sketch 002
  shows previews as dimmed rows). The middleware runs before pydantic validation, so a client
  value is coerced the way the tool's validation coerces it (the string `"false"` is `false`)
  before it is recorded: a real write is never recorded as a preview, nor a preview as a write.
- **D-03:** "Every audit record" means the per-call middleware envelope. The `mail_recover`
  `plan`/`done` receipts stay unchanged: they exist only on the real path. Old records are not
  migrated; every reader (`audit_read`, `find_receipt`, the `audit` tool) already uses `.get()`
  and must keep reading a record that has neither key.
- **D-04:** `caller` names the real MCP client, forwarded by the shim (owner, 2026-10-12).
  Today the daemon sees `mcp 0.1.0` and a new session on every call (FastMCP 3.4.7
  `fresh_client_factory`). `daemon.run_shim` replaces `create_proxy(...)` with
  `FastMCPProxy(client_factory=f)`. `f` returns `_Client(transport, client_info=...)` that copies
  the shim session's `get_context().session.client_params.clientInfo` (name, version) and adds a
  stable shim id, made once per shim process, as an extra `clientInfo` field
  (`Implementation` allows extras). `f` falls back to a fixed shim identity when `client_params`
  is `None` (the `initialize` path, `fastmcp/server/providers/proxy.py:90`) or `get_context()`
  raises (`ping_remote`, `proxy.py:921`).
- **D-05:** Record shape: `caller` is a string `"<name> <version>"` (sketch 004's `dashboard` is
  the precedent for a string). The shim id goes in a second key (`session`) when present. In stdio
  mode the record takes the client's own `clientInfo`. With no `clientInfo` (in-process calls, a
  CLI, the `SimpleNamespace` test contexts) `caller` is a fixed fallback and the middleware
  tolerates a missing `fastmcp_context`.
- **D-06:** The shim change keeps the #170/#302 invariants: `Timeout(None, connect=10.0)` and
  `fail_loud_on_dead_stream` stay untouched. Tests: an in-memory `fastmcp.Client(srv.mcp)` calls a
  write tool without `dry_run` and its record says `dry_run: true`; a unit test drives the shim's
  client factory and proves the forwarded `clientInfo`, the shim id and both fallbacks. The
  build's stream smoke (`scripts/smoke_stream.py`) and the D-14 device run cover the live path.

## Summary

Six requirements split into three groups. FIX-01 and FIX-06 are fully researchable now. FIX-02, FIX-03 and FIX-04 need the iMac probe, so this research fixes what the probe must measure and maps each result to a fix route. FIX-05 is a build-and-install procedure with three traps that the discussion did not see.

The FIX-01 design in CONTEXT works. A probe of the full chain (front client, `FastMCPProxy(client_factory=f)`, Streamable HTTP over a real unix socket, daemon-side middleware) shows the daemon reads the copied `clientInfo` name, version and the extra `session` key. The `initialize` call hits the `client_params is None` fallback and `ping` hits the `get_context()` RuntimeError fallback, as D-04 says. Pydantic coerces `"false"`, `"0"`, `"no"`, `"off"` and `0` to `false`. It rejects `" false"` and `None`. A rejected value makes the call fail, so the middleware writes no record for it.

The main findings the planner must act on:

1. **FIX-05 trap: `build_app.sh --sign` without `--notarize` writes no zip.** The `ditto -c -k` step sits inside the `--notarize` branch. D-12 needs a manual `ditto -c -k --keepParent` step before the draft upload.
2. **FIX-06 scope: two more tracked files carry the firmware detail.** `CHANGELOG.md:72` and `.planning/debug/mail-index-schema-sequoia.md:34` match the removed-terms check, beside the four files in D-16. Success criterion 6 says "every tracked file". The planner needs a decision on the CHANGELOG (a published release note).
3. **FIX-03 premise detail: `notes_all` caps at 25 (`MAX_NOTES`).** The criterion "same count as Notes.app" holds only up to 25. The probe must compare `min(25, n)`.
4. **FIX-04 side effect: one existing unit test asserts the behavior D-11 changes.** `tests/test_mail_search.py:867-868` expects the raw UUID for an account missing from a non-empty map.
5. **CI trap: `version.yml` fails any PR that edits `pyproject.toml` without a version bump.** No Phase 03.1 code PR may touch `pyproject.toml` or its dependency list. `from pydantic import TypeAdapter` needs no declaration: `mcp` requires `pydantic<3,>=2.11`.
6. **CI trap: CI runs the suite twice, the second time with `MACOS_APPS_READ_ONLY=1`.** Write and send tools are then unregistered. FIX-01 tests must read `registry.TOOLS` (all records) or use a local FastMCP server, never the filtered views.
7. **`scripts/smoke_stream.py` does not exercise `run_shim`.** It tests the transport and the dead-stream wrapper only. D-06's "covers the live path" is true for the transport, not for the new client factory. Extract the factory into a testable function and prove it in a unit test over a real unix socket (pattern in `tests/test_daemon.py`).

**Primary recommendation:** Ship FIX-01 as one TDD lane (registry view, middleware, shim factory, tests). Run the iMac probe in parallel with the exact scripts below. Make the FIX-06 scrub two PRs (`.planning/`-only, and docs+CHANGELOG). Build the `.app` last, zip it by hand, and move it through a draft release.

### Pattern 2: Middleware resolution (D-02, D-05)

```python
# audit.py (module level; pydantic is a transitive dep of mcp>=1.26,<2 — see Standard Stack)

_BOOL = TypeAdapter(bool)

def _resolve_dry_run(tool, args, defaults) -> bool:
    if "dry_run" in args:
        try:
            return _BOOL.validate_python(args["dry_run"])   # same lax coercion as the tool call
        except ValidationError:

def _caller(context) -> tuple[str, str | None]:
    fc = getattr(context, "fastmcp_context", None)          # SimpleNamespace test contexts have none

    except (AttributeError, RuntimeError):
```

```python
def _shim_client_factory(transport, shim_id: str):
    """Returns f() -> Client. One transport object is shared, as client.new() shares it today."""
    from fastmcp.server.dependencies import get_context
    from mcp.types import Implementation
```

### Anti-Patterns to Avoid
- **Writing `dry_run` into `args`.** D-01 says `args` stay as sent. The sketches read the resolved flag from the new top-level key.
- **Filtering with `registry.audit_verbs()` or `write_tools()` in new tests.** They are empty under `MACOS_APPS_READ_ONLY=1`. Read `registry.TOOLS`.
- **Adding a read timeout to the shim↔daemon hop** to "fix" anything. Forbidden (#170).
- **Editing `pyproject.toml` or `uv.lock` in a code PR.** `version.yml` fails it without a bump. (`uv run` can also rewrite the `uv.lock` revision line; memory `uv-lock-revision-on-release-bump`. `git status` after `uv run`: it was clean in this session.)
- **Importing `run_osascript` by name** in `contacts.py`, `mail.py` or `mail_addressing.py`. `tests/test_native_seam.py` forbids it.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Bool coercion of a client `dry_run` | A string table (`"false"`, `"0"`, …) | `TypeAdapter(bool).validate_python` | Pydantic lax mode accepts `"false"`, `"0"`, `"no"`, `"FALSE"`, `0` and rejects `" false"`, `"banana"`, `None` (probe below). A hand table drifts. |
| Client identity forwarding | A custom MCP message or header | `Client(client_info=Implementation(..., session=…))` | `Implementation` already allows extras; the daemon reads the same object. |
| One-line, control-free label from untrusted `clientInfo` | New sanitizer | `text.clean_summary` | Already used for every Pointer summary; bounded at 200. |
| Draft-release asset fetch | `curl` against the REST asset URL | `gh release download` | `gh` resolves a draft by tag (GraphQL, then REST by id) and downloads with the authenticated client. |
| Read-only SQLite open on the iMac | Python helper | `sqlite3 -readonly "file:…?mode=ro"` | Same URI form as `runtime._open_sqlite_ro`. Validated below. |
| Reachability proof of the daemon | New harness | `.worktrees/.daemon_probe.py` pattern | Exists, but see Pitfall 8 for what it does not cover. |

**Key insight:** every piece of FIX-01 is a view or a parameter on code that already exists. The risk is in where it runs (daemon versus shim) and in the CI second pass (READ_ONLY), not in the logic.

## Common Pitfalls

### Pitfall 1: `dry_run` coercion mismatch records a real write as a preview
**What goes wrong:** the client sends `"false"` (a string). The middleware reads `args["dry_run"]`, sees a truthy string, records `dry_run: true`; the tool coerces it to `False` and acts.
**Why:** the middleware runs before pydantic validation (D-02).
**How to avoid:** coerce with `TypeAdapter(bool)`. Table measured in this session on FastMCP 3.4.7 (tool `w(dry_run: bool = True)`):

| Client sends | Tool receives |
|---|---|
| omitted | `True` (the default) |
| `"false"`, `"FALSE"`, `"0"`, `"no"`, `0` | `False` |
| `"1"`, `"yes"` | `True` |
| `"banana"`, `" false"` (leading space), `None` | validation error, call fails, no record |

[VERIFIED: probe 1 output, 2026-10-12]. Add a parametrized test over this table, and a test that an invalid value writes no record.
**Warning signs:** a test passes only for real booleans.

### Pitfall 2: tests that pass locally and fail in CI's READ_ONLY pass
**What goes wrong:** a test calls `srv.delete_event` through `Client(srv.mcp)` or reads `registry.write_tools()`. Under `MACOS_APPS_READ_ONLY=1` the tool is absent.
**How to avoid:** unit-test `dry_run_defaults()` over `registry.TOOLS`. For the end-to-end test required by the success criterion, build a local `FastMCP("t")`, register a function `def delete_x(id: str, dry_run: bool = True)`, add the real `AuditMiddleware` with `audit_verbs={"delete_x": "delete"}` and `dry_run_defaults={"delete_x": registry._dry_run_default(fn)}`, and call it through `Client(app)` without `dry_run`. Also assert the real `registry.dry_run_defaults()` equals the D-02 list.
**Warning signs:** `uv run pytest` green, `MACOS_APPS_READ_ONLY=1 uv run pytest` red. Run both before each PR.

### Pitfall 3: `scripts/smoke_stream.py` does not test the new shim path
**What goes wrong:** the plan trusts the build smoke to prove the factory. The smoke builds its own `Client(StreamableHttpTransport(...))` and never calls `run_shim` [VERIFIED: scripts/smoke_stream.py lines "t = StreamableHttpTransport(…)" / "async with Client(t) as c"].
**How to avoid:** extract the factory (Pattern 3) and add a unit test in `tests/test_daemon.py` using `_serve(app, path)` (that file's helper at lines 113-125): an app whose middleware returns `clientInfo`, a `FastMCPProxy(client_factory=…)` in front, a front client with a known `client_info`. Assert name, version, the shim id (stable across two calls, different across two factories) and both fallbacks. Optionally extend `smoke_stream.py` to call one tool through the same factory so the bundled libraries (#286) cover it on both slices.

### Pitfall 4: `build_app.sh --sign` produces no zip
**What goes wrong:** D-12 runs the script with `--sign` only. The zip is created inside `if [[ -n "$NOTARIZE" ]]; then ditto -c -k --keepParent "$APP" "$OUT/macos-apps-mcp.zip" …` [VERIFIED: scripts/build_app.sh:255-259]. Without `--notarize` the output is the `.app` directory alone.
**How to avoid:** add an explicit step: `ditto -c -k --keepParent dist/macos-apps-mcp.app dist/macos-apps-mcp.zip`, then `shasum -a 256`. If the owner chooses to notarize (Claude's discretion), the script's zip is made BEFORE stapling and is only the submission transport. Re-zip after `stapler staple` (memory: notarization-setup). Check `xcrun notarytool history --keychain-profile notary` exits 0 before a notarized build.

### Pitfall 5: the `-dirty` stamp and untracked files
**What goes wrong:** the stamp is `$(git -C "$REPO" describe --always --dirty --exclude '*')` [VERIFIED: scripts/build_app.sh:107-108]. `--dirty` flags modified tracked files only. The wheel is built by `uv pip install … "$REPO"` (line 103) from the working directory. An untracked file in the tree can enter the build without changing the stamp.
**How to avoid:** build from a fresh locked worktree created from `origin/develop` HEAD, with nothing else in it. Verify `git status --porcelain` is empty and `git rev-parse HEAD` equals `origin/develop` before building. After the build, read `Contents/lib/python3.14/site-packages/macos_apps_mcp/build_stamp` (path from build_app.sh:77 `SITE=…/python${PYVER}/site-packages` and line 108). The first token must equal the abbreviated sha, with no `-dirty`.

### Pitfall 6: a draft release might create a git tag
**What goes wrong:** `gh release create --help` says a missing tag "will automatically get created from the latest state of the default branch" [VERIFIED: `gh release create --help`]. If a draft creates the tag early, a stray `imac-build-*` tag stays after the draft is deleted.
**How to avoid:** pass `--draft --target <full sha>`. After creation run `git ls-remote --tags origin 'refs/tags/imac-build-*'`; expect nothing [ASSUMED: a draft does not create its tag until published; confirm with the ls-remote]. Delete with `gh release delete <tag> --yes --cleanup-tag` (flag exists [VERIFIED: `gh release delete --help`]). No workflow triggers on tags [VERIFIED: ci.yml triggers `push: branches [develop, main]` and `pull_request`; publish.yml triggers `push: branches [main]` and `workflow_dispatch`; version.yml triggers `pull_request` on paths], so a stray tag starts no job.

### Pitfall 7: `gh release download` on a draft needs repo-write auth on the iMac
**What goes wrong:** drafts are visible only to users with push access.
**What is known:** `gh` finds a draft by tag through GraphQL (`RepositoryReleaseByTag`, rejecting non-drafts) and then fetches `releases/{id}` by REST; its comment reads "First use GraphQL to find a draft release by pending tag name, since REST doesn't have this ability." Assets download from each asset's `APIURL` with `Accept: application/octet-stream` through the authenticated client [CITED: https://raw.githubusercontent.com/cli/cli/trunk/pkg/cmd/release/download/download.go · [🔖 2026-10-12](https://linkding.lav.ren/bookmarks?details=1285)].
**How to avoid:** D-13 already makes this the first iMac step. The check: `gh auth status` and `gh release download <tag> --repo elfensky/macos-apps-mcp -p 'macos-apps-mcp.zip' -D <dir>`. Whether the iMac's `gh` is logged in with a token that has push access is unknown (no observation; the session is offline). Stop and ask on failure, as D-13 says.

### Pitfall 8: `.worktrees/.daemon_probe.py` is not a shim proof
**What goes wrong:** it connects with a plain `Client(StreamableHttpTransport(…uds…))` [VERIFIED: .worktrees/.daemon_probe.py, `transport = StreamableHttpTransport("http://daemon/mcp", httpx_client_factory=_uds_client_factory(socket_path()))`].
