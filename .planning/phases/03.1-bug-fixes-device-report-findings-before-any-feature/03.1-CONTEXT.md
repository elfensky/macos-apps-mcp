## Implementation Decisions

### Audit record: resolved dry_run and caller (FIX-01, #222)
- **D-01:** `AuditMiddleware` resolves `dry_run` for each call from the tool's signature default.
  A new registry view `registry.dry_run_defaults()` (next to `audit_verbs()`, derived from
  `inspect.signature(rec.fn).parameters.get("dry_run")`) gives the defaults to the middleware at
  construction, the same way `audit_verbs` is given. `args` stay exactly as the client sent them.
  The envelope gets two new top-level keys: `dry_run` and `caller`. No tool body changes.
- **D-02:** Every middleware record carries a boolean `dry_run`. Eleven tools default to `true`:
  `delete_draft`, `move_mail`, `trash_mail`, `mail_undo`, `send_mail`, `reply_all`,
  `forward_mail`, `delete_reminder`, `delete_event`, `delete_note`, `update_note`.
  `update_mail_status` and `run_shortcut` default to `false`. A tool with no `dry_run` parameter
  always acts and records `false`. Previews stay in the log and `op` keeps its verb (sketch 002
  shows previews as dimmed rows). The middleware runs before pydantic validation, so a client
  value is coerced the way the tool's validation coerces it (the string `"false"` is `false`)
  before it is recorded: a real write is never recorded as a preview, nor a preview as a write.
- **D-03:** "Every audit record" means the per-call middleware envelope. The `mail_recover`
  `plan`/`done` receipts stay unchanged: they exist only on the real path. Old records are not
  migrated; every reader (`audit_read`, `find_receipt`, the `audit` tool) already uses `.get()`
  and must keep reading a record that has neither key.
- **D-04:** `caller` names the real MCP client, forwarded by the shim (owner, 2026-10-12).
  Today the daemon sees `mcp 0.1.0` and a new session on every call (FastMCP 3.4.7
  `fresh_client_factory`). `daemon.run_shim` replaces `create_proxy(...)` with
  `FastMCPProxy(client_factory=f)`. `f` returns `_Client(transport, client_info=...)` that copies
  the shim session's `get_context().session.client_params.clientInfo` (name, version) and adds a
  stable shim id, made once per shim process, as an extra `clientInfo` field
  (`Implementation` allows extras). `f` falls back to a fixed shim identity when `client_params`
  is `None` (the `initialize` path, `fastmcp/server/providers/proxy.py:90`) or `get_context()`
  raises (`ping_remote`, `proxy.py:921`).
- **D-05:** Record shape: `caller` is a string `"<name> <version>"` (sketch 004's `dashboard` is
  the precedent for a string). The shim id goes in a second key (`session`) when present. In stdio
  mode the record takes the client's own `clientInfo`. With no `clientInfo` (in-process calls, a
  CLI, the `SimpleNamespace` test contexts) `caller` is a fixed fallback and the middleware
  tolerates a missing `fastmcp_context`.
- **D-06:** The shim change keeps the #170/#302 invariants: `Timeout(None, connect=10.0)` and
  `fail_loud_on_dead_stream` stay untouched. Tests: an in-memory `fastmcp.Client(srv.mcp)` calls a
  write tool without `dry_run` and its record says `dry_run: true`; a unit test drives the shim's
  client factory and proves the forwarded `clientInfo`, the shim id and both fallbacks. The
  build's stream smoke (`scripts/smoke_stream.py`) and the D-14 device run cover the live path.

### Device investigation: probe first (FIX-02, FIX-03, FIX-04)
- **D-07:** Wave 1 holds one iMac probe plan (`autonomous: false`) through the Remote Control
  session `REMOTE imac2012 (macos-apps-mcp)` against the installed 0.14.3 daemon. The owner is
  asked before the run. Reads are read-only and count-only: results carry no titles, names,
  addresses or account names. No family account is touched; any test item is a throwaway. One
  diagnostic re-run per failed check. The iMac session never commits or pushes; it returns
  results by SendMessage and the main session records them. A result that overturns an issue's
  premise is a valid deliverable and is stated first.
- **D-08:** The owner sits at the iMac once (owner, 2026-10-12). The plan stops at a checkpoint
  for that sitting. The owner answers the one Terminal → Contacts Automation prompt (and Mail's,
  if D-11 needs it), so the raw scan is timed outside the daemon as criterion 2 asks, and reads
  the note count Notes.app shows outside Recently Deleted (D-10). In that sitting the probe
  measures, for Contacts:
  - narrow (one full family name) and broad (`"an"`) `contacts()` through the daemon;
  - the current loop script (`repeat with p in (people whose name contains q)`) with no host cap;
  - the `(get people whose name contains q)` form;
  - the bulk form, one Apple event for each property (`id of (people whose …)`, `name of …`,
    `organization of …`, `value of phones of …`, `value of emails of …`);
  - Contacts' process state and CPU during each run;
  - the person count and the `"an"` match count from a count-only read of
    `~/Library/Application Support/AddressBook/Sources/*/AddressBook-v22.abcddb` (check the
    entity name in `Z_PRIMARYKEY` first).
- **D-09:** The FIX-02 fix follows the measured cause:
  - (a) Each property read re-runs the `whose` scan: a bulk read — whichever of the `get` form or
    the one-event-per-property form the probe measured faster.
  - (b) One scan alone is slow but progressing: a contacts-specific host cap of about 3× the
    measured broad query, with the script backstop at or above the host cap (GATE-10,
    `tests/test_applescript_timeout.py`), as `mail_triage._TRIAGE_TIMEOUT` does.
  - (c) Contacts is blocked or idle: an error text that names the real cause.
  The #95 SQLite plane is not built (CON-04 is v2). Route (a) is not one of the two fixes the
  roadmap named; ROADMAP criterion 2 and FIX-02 now include it (this records PR).
- **D-10:** FIX-03 (#335) is settled by one grouped count-only query on the iMac over the four
  `_FROM` conditions (`adapters/notes.py`): no `ZNOTEDATA`, no `ZFOLDER`, `ZMARKEDFORDELETION`
  set, folder titled "Recently Deleted"; plus the count of rows whose `Z_ENT` is `ICNote` (by name
  through `Z_PRIMARYKEY`), plus which plane answered `notes_all` (SQLite or the AppleScript
  fallback). The exact read-only `sqlite3 "file:…?mode=ro"` command is written into the brief, so
  the session's permission classifier does not block it again. Same count as Notes.app: no code
  change, #335 closes with the record. A live note dropped: the fix stays inside the
  `_FROM`/`_FINGERPRINT` strings.
- **D-11:** FIX-04 (#336): the probe compares the stray UUID with `get id of every account`, with
  `~/Library/Mail/V10/<uuid>` and with that account's mailbox totals, and calls `mail_overview`
  once after `launchctl kickstart -k`. The expected cause is a removed account whose rows stay in
  the Envelope Index (the same defect as iret77/apple-mail-mcp#25). Fix for that cause:
  `overview()` labels an id that Mail does not list `"(account not in Mail)"`, only after
  `account_map()` answered with a non-empty map (a cold cache makes every id look unknown);
  `account_id` stays the machine-readable value; the `mail_overview` docstring and the
  integration test that accepts "named or uuid" are updated. If the cause is an account added
  after the map was cached, the fix is one map re-read on an unknown UUID, limited by the
  existing `_ACCOUNT_MAP_FAILURE_TTL`. The cause is recorded on #336 either way.

### End-of-phase build on the Intel iMac (FIX-05, criterion 5)
- **D-12:** After every code PR of the phase is merged, the `.app` is built on this Apple-silicon
  Mac from a clean locked worktree at `origin/develop` HEAD:
  `scripts/build_app.sh --sign "Developer ID Application: Andrei M. Lavrenov (VUMUR696L9)"`

  `doctor().build` names the commit, with no `-dirty`. This is not a release: no version bump, no
  `main` merge, no tag, no PyPI.
- **D-13:** The zip reaches the iMac as an asset of a **draft** GitHub release (owner,
  2026-10-12). The draft uses a non-version tag name (for example `imac-build-<short-sha>`), is
  never published, and is deleted after the install. The iMac session fetches it with
  `gh release download`. The first step proves the iMac session's `gh` can download a draft asset
  (auth and draft lookup); if it cannot, the plan stops and asks. The sha256 is compared on both
  Macs. `gh` sets no quarantine xattr, so notarization is not required on this route; the install
  step reads `xattr` and stops if quarantine is present.
- **D-14:** The install repeats the 0.14.3 procedure: move the old app to
  `~/.local/state/macos-apps-mcp/app-backup/`, `ditto` the new bundle into `/Applications` (never
  over a bundle still in place), `launchctl kickstart -k`, then `doctor()` names the commit.
  Then, through the daemon: `doctor(request=True)` with Photos quit reports photos ok

  forwarded `caller` in its audit record. Probe exits are read with `$?`, never `PIPESTATUS`.

### Established Patterns
- Probe before code: a probe that overturns an issue's premise is a valid deliverable.
- Device plans split at every owner action; the iMac session drives the daemon through a
  scripted client on the bundle shim.
- Our count disagrees with the app's own count: our query is wrong until proven otherwise.
- Thin dispatch: no business logic in `server.py` tool bodies.

### Integration Points
- `server.py` middleware construction is where `dry_run_defaults()` enters `AuditMiddleware`.
- `daemon.run_shim` is the only place the shim builds its proxy; the daemon reads `clientInfo`
  from `context.fastmcp_context.session.client_params.clientInfo`.
- `build_app.sh` writes `<short-sha>[-dirty] <utc>`; `doctor._build_stamp()` reads it.

## Specific Ideas

- The Contacts loop most likely costs about 1 + 50 × 9 ≈ 450 `whose` scans for a broad query
  (`MAX_CONTACTS = 50`, about nine property reads per person). The module comment that calls the
  scan "one cheap Apple Events call" is wrong and is corrected with the fix.
- At the second #334 failure Contacts sat in state S at 0.0% CPU, which does not fit repeated
  scans. The probe must tell a blocked Contacts from a slow loop before any fix is chosen.
- Research (2026-10-12): a live `ICNote` must have `noteData` (non-optional in the macOS 27
  NoteData model), so a NULL `ZNOTEDATA` is an unlikely cause for #335; the iMac's macOS 15 model
  was not inspected.
- Research (2026-10-12): `gh release download` writes no `com.apple.quarantine` xattr (tested
  with gh 2.102.0 on this Mac); AirDrop does.
